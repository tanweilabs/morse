# Changelog

Notable changes, newest first. Morse is pre-release, and several AI agents build it by talking to each other through it, so this log also records the bugs that changed the design. [CHANGELOG.zh-CN.md](CHANGELOG.zh-CN.md) has the day-by-day detail.

## Unreleased

### The remaining anytoany code is replaced (ADR-093)

- Every part of the public tree still written by the original anytoany author is rewritten as Morse's own code with the same behaviour: the delivery adapters, the daemon's local API and dispatcher, the mailbox, external agents and the 闪电说 integration, the Claude doorbell and session liveness, device identity and trust, the CLI's older command wiring, the prompt hook, doctor and setup, the web console, the skills' wording, CI, configs. His tests are replaced by new ones (2035 → 2158 tests).
- Deleted as dead: the device-ID LAN (mDNS `_anytoany._tcp` + mutual TLS, not started since ADR-091), `scripts/smoke.sh`, `scripts/lan-smoke.sh`, `scripts/experiments/`, the root `install.sh` (the installer is `site/install.sh`), static test fixtures.
- Docs: current specs and research rewritten briefly; obsolete 2026-08 research, archived specs and the founding analysis no longer exported. The anytoany-era changelog entries are condensed below.
- Small deliberate changes: a JSON-lines record that is not an object is skipped like a corrupt line; `morse hook` with non-object input prints `{}`; a `config.json` holding an array reads as `{}`; the first desktop notification for a session is always shown; the 闪电说 instructions have new wording (same commands), so `morse setup` refreshes them once.
- The npm package name stays `anytoany`. `LICENSE-MIT` and `NOTICE` are still there; whether they go is the maintainer's call.

### Windows: direct WebRTC links are on (ADR-080 #33–37, phase 5, first half); stopping hangs up direct links at once (all platforms)

- Windows no longer forces direct links off: `direct` is gone from the Windows "off in this release" list (`src/platform/platform.ts`), and the daemon there takes the same path as macOS / Linux — on by default, off with `"morse": {"direct": {"enabled": false}}` or `MORSE_DIRECT=0`; about 3 s to open, else the relay; a device that does not answer is left to the relay for 5 minutes (doubling, up to 6 h). `morse status` shows the usual `direct:` line on Windows. The LAN stays off there.
- Tried on a real Windows 11 (Node 22.23.5) against a Mac on the same router: `node-datachannel`'s win32-x64 build loads; messages both ways and 2.4 MB files both ways went `delivered via direct`; a 38 MB transfer whose link dropped half-way fell back to the relay and completed (SHA-256 checked); restarting the Windows daemon with a link open — the next message opened a new link. Only host / prflx candidates were selected (same LAN); srflx candidates from stun.cloudflare.com were gathered. Not tested yet: two different networks, and a Windows with no existing firewall rule for `node.exe`.
- Fix (all platforms): an orderly stop closed direct links in a `setImmediate` that never ran — the process exited first, so the other side only noticed after ~30 s of ICE timeout and every chunk sent in that window was lost. `close()` now hangs up at once; on the real pair the other side noticed in ~35 ms instead of 28 s.
- Installer, skill and site texts no longer say Windows has no direct links.

### Removing v2, follow-ups: the LAN is off by default and hardened; the upgrade never widens permissions; people blocked by old name stay out; mail to an old name is no longer "delivered" (ADR-091)

- The LAN by address is OFF unless `morse.lan: true` in config.json or `morse start --lan`. When on, it is hardened:
  - only the first address is announced;
  - before anything goes to a computer, it must prove it holds that address's key (it signs a nonce); of several computers announcing one address only a proven one is used;
  - only messages go there, each confirmed by its receipt — none within a few seconds and it goes by WebRTC / the relay, and that address skips the LAN for 10 minutes; chunks, receipts, notices and signals never go over the LAN, so someone on the network can no longer stall a file transfer or swallow receipts;
  - the listener opens an envelope (signature, an address hosted here) before taking it and answers `202 {}` whatever it found; JSON only, never from a browser (`Origin`); at most ~1.1 MB; 5 s header / 15 s request timeouts; at most 32 connections; 120 requests a minute and 5 new senders per 10 minutes per IP; a bounded peer list.
- Attendant settings written for an old name keep applying and never widen: the handle of a contact's old name (`alice` for `alice/air`) and a remark dropped when the upgrade merged two rows (recovered from the v5 backup into the new `contact_old_keys` table) are lookup keys too. Tested by comparing every contact's effective profile before and after the upgrade.
- Someone blocked by old name (a declined request, a removed contact — no address in `morse-blocked.json`) who writes the old way again is recognised by that name, dropped, and their address is blocked too.
- Mail to an old name waiting in the outbox fails for good with the one line (it was marked delivered to the local inbox); rows the release before mis-marked are failed on the next open.
- Old-name mail for a second agent (`mei/<agent2>`) is filed for that agent; the "accepted" notice to a stranger who wrote the old way carries the certificate so their held messages come at once (nobody else's does: the first and second addresses still speak alike).
- The own-inbox session of ADR-061 has nothing left to run: it only took mail from your other computers, which are contacts now.
- Mail from another computer is always a peer's, whatever tier is stored with it (also when a daemon of the release before files your old computer's mail as owner); rows moved by the upgrade are set to peer.
- A contact without a remark gets its old name as remark (when taken, lines show `(was <old name>)`); leftover agent rows of other computers under yourself are removed.
- A failed upgrade backup is one line and exit 1 — no stack trace, no daemon crash loop; the upgrade line also mentions contacts put into `self` by hand.
- Homes already at v5 are repaired once on open (`repairAfterV5`, mark `p5.repair.1`; old values in `~/.morse/backups/repair-remove-v2-<time>/changes.json`).

### Removing v2, stage 2: the client sends nothing the v2 way; an old name is one error line; pairing, invites and `agent` are gone (ADR-091)

- No v2 connection, no v1 envelopes, no lookups of old names. Mail a released client (20261116042458 on) writes to your old name — a certificate-bearing v3 envelope on the v3 connection — still comes in, filed by the address that signed it, and its receipt carries the certificate (from the first address only). A v1 envelope (only a client with no v3 at all sends one) is dropped with a log line.
- An old name is one line: `morse send` / `contact add` … with `morse.im/<old name>`, `<old name>/<agent>`, `me/<agent>`, or to a contact by old name with no address known, say `<who>: old names no longer work — ask for their 26-character address (morse address shows it)` and send nothing. `morse address` shows no `old name:` line.
- Removed hidden commands (now unknown commands): `pair`, `peers`, `join`, `invite`, `relay` (incl. `relay show`), `device`, `name`, `agent` / `agents`. Addresses are managed with `morse address [add | set | remove]` only.
- Message lines name the contact (remark or address), not `claude → mini`; JSON only gains fields (`oldName`).
- Installers (`install.sh`, `install.ps1`): no invite or pairing codes (given one, they say what to do instead), no `join`; `morse address` makes the address when there is none. `--agent` / `--name` are accepted and ignored.
- A peer too old for addresses: `… their Morse is too old to be reached by address (…) — ask them to update: run the installer again (morse.im)` — there is no old link to fall back on. `morse status --check` no longer talks about paired devices.
- Fixed a stage-1 bug: the daemon's LAN layer failed to start (`lan: off — Cannot access 'morse' before initialization`), so the LAN by address never ran in a real daemon (unit tests drive the module directly).
- Skill, READMEs, QUICKSTART and the home page follow: old names no longer work, another computer of yours is an ordinary contact in group `mine`, the LAN goes by address.
- Tests: new `test/released-interop.test.ts` (a home written by the released code is migrated by this one, then mail goes both ways with two released peers and with the owner's own computer still on the release) and `scripts/morse-e2e-addresses.sh` (local `wrangler dev` relay, two throw-away homes, real mDNS by address); seven v2-only test files removed.

### Removing v2, stage 1: the client needs no v2 at all; every contact by its address; your computers paired the old way are ordinary contacts in group `mine` (ADR-091)

- The v3 connection opens at start — it no longer waits for a v2 login to announce protocol 3. The v2 connection is only opened on a computer that already has an old name (`relay.handle`): to take v1 envelopes from people who have not updated, and to reach a contact by old name whose address is not known. A computer installed since never logs in the v2 way.
- New installs register no old name: the first `morse address` (and the plain `morse join` the installers run) makes the key and address here and writes the relay — no request. `morse address add` / `remove` change this computer only (no `/v1/agents`), and work with the relay unreachable.
- Sending: a contact with a known address is reached by it — whatever it was called before, paired the old way or not.
- Receiving: every v3 envelope (with or without a device certificate) is decided by the address that signed it — blocks, contacts and message requests by address; an old name or agent name the sender writes is not read. An answer to someone who wrote the old way still carries this computer's certificate (their client takes no other). There is no owner tier any more: another computer's mail never carries your authority, never picks or resumes a session.
- The mailbox goes to `user_version` 5 (one transaction; ONE small backup taken inside it by the migrating process, `~/.morse/backups/remove-v2-<time>/`; idempotent; safe against SIGKILL, concurrent openers and a still-running older process):
  - a contact by old name whose address is known (checked by the P2 split, seen, the signer of mail filed under it, or the pinned certificate of the one paired computer of that name) becomes a contact by address; the old way of writing it is kept in `old_name` (`oldName` in JSON); remark, group, permissions and history unchanged. One whose address cannot be told stays, marked `— needs their new address` in `morse contact` (`needsAddress: true`), never deleted.
  - every contact in group `self` (your own computers paired the old way, and anyone put there by hand) is in group `mine`, without the `own-device` mark. **Their messages are no longer taken as your own instructions**; to let one act for you: `morse contact set <it> --cwd <dir> --tools <tools>` (or set the `mine` group). `--group self` is refused from now on (`self` is you).
  - a block by old name blocks every address known for it at the first address (`morse-blocked.json` untouched); a request by old name from a computer whose certificate is pinned becomes a request by address; outbound mail not confirmed yet that was written to an old name is written to the contact's address.
  - said once: `morse: old names are gone — every contact is reached by its address now; N contact(s) need their new address (ask them for it, then: morse contact add morse.im/<address>); N contact(s) — your own computers paired the old way among them — are in group mine: ordinary contacts, their messages are no longer taken as your own instructions (to let one act for you: morse contact set <name> --cwd <dir> --tools <tools>); nothing was deleted, backup: <path>`. `morse status` gains a `contacts: reached by address — …` line. Restoring by hand: `docs/guides/restore-contacts-backup.zh-CN.md`, part one.
- LAN by address: mDNS `_morse._tcp` announces addresses only (no device name or ID); `POST /v3/envelope` carries the same v3 envelopes as the relay, authenticated by their signatures — no pairing, trust list or mutual TLS. The device-based LAN (`_anytoany._tcp`, mutual TLS, `/api/peer/*`, other computers' session directories) is off; a computer not updated yet does not see you on the LAN and goes through the relay. `morse start --peer <address>@<host>:<port>` names one without mDNS.
- Direct (WebRTC) links by address: between this computer's first address and a contact's address, signaled over the v3 connection with v3 envelopes; an open link is no longer closed by a late candidate signal that fails because the relay went away.
- A daemon of the release before that is still running: commands that change contacts or send refuse and say to restart it (new capability `addresses-only`).
- The hidden `morse agent` (list) no longer drops addresses added here only from this computer's list.

### `morse read`: messaging is three verbs — send, reply, read; `morse message` stays as a hidden alias (ADR-090)

- `morse --help` lists `read`, `send`, `reply`, `contact`, `address`. `morse read` is exactly what `morse message` was: no argument = what is waiting to be processed (+ the count of message requests); `read <contact>` = everything with one contact; `read --id <id>` = one in full; every option (`--all`, `--from`, `--all-addresses`, `--pull`, `--wait`, `--history`, `--inbox`, `--json`, `--limit` …) the same, output byte for byte the same.
- Reading changes nothing: a message stays to process until `morse reply` or `morse done` (only `--pull` / `--take` take what they show, as before). The help and the skill say so.
- `morse message` (and `messages`) keep working unchanged — skills, plugins, hooks and scripts call them; the plugin JSON contract is unchanged. `morse help --all` lists `message` among the hidden commands.
- The old hidden `morse read <id>` keeps working: `read <arg>` is a message when the argument is a message id or a unique prefix, else a contact; when it is both (a hex remark that is also an id prefix) it is the message, with one `note:` line on stderr naming the contact's address. No match: the old `no message <id>` error when the argument looks like an id (hex with a digit), the contact error otherwise.
- Every hint now says `morse read …`: the prompt hook's line (`[morse] N new messages from … — morse read`), the to-process footer, send / outbox errors, accept / contact add, `morse connect`, the Windows notes, install.sh / install.ps1, the attendant's and the WeChat bridge's notices, the skills, `agent.md`, README, QUICKSTART and the plugin docs.

### Restarting: every hint says `morse stop --restart`; `morse start` no longer makes a second, unmanaged daemon (ADR-089 follow-ups)

- On a computer where launchd / systemd runs the daemon, `morse stop` followed by `morse start` used to leave a hand-started daemon outside the service manager: its own copy then failed every 10 seconds with "already running", and an automatic update could not restart the one that was running. `morse start` now hands the start to launchd / systemd there (where there is no service job, it starts in the foreground as before), and every hint that said `morse stop && morse start` says `morse stop --restart`.
- A killed agent CLI is noticed when the process exits, not when its output pipes close — a child of it that kept them open used to delay that until the time limit, and the message was then reported as timed out.
- Before the service manager is asked to start, stop or restart anything, the job is checked to be this home's own (the file launchd / systemd loaded it from).
- Documented: killing an agent's process on purpose does not cancel its message — it is delivered again with the warning, up to three turns. To stop a message for good: `morse done <id>`.

### A restart in the middle of an agent's turn no longer delivers the message twice (ADR-089)

- **What went wrong:** when the daemon restarted (an update, `morse stop && morse start`) while one of your agents was still working on a message, the message was handed out again 30 seconds later — the agent did the same thing twice. Typing a prompt in that session right after the restart pulled the message in a second time as well.
- **A delivery now belongs to whoever holds it.** The dispatch plugin claims a message under a lease, renews it while the turn runs and ties it to the agent CLI's process. As long as that turn is running nobody else gets the message — not a new plugin, not the prompt hook, not `morse message --pull`. Only the holder's report counts; a late report from a delivery that was taken over changes nothing, and its answer is not sent.
- **A restart waits for the turn:** an update waits for a quiet moment before it installs (at most 10 minutes) and again before it restarts (at most 2) — `morse status` says so while it waits. A plugin that is told to stop lets a running turn finish for up to 10 seconds; the daemon signals it once and gives it 15 seconds instead of 3. An update no longer restarts with `launchctl kickstart -k` straight away (launchd kills a job 5 seconds after that, measured): the daemon stops in its own orderly way first, then the service manager restarts it. New installs get `ExitTimeOut` 30 (launchd) and `KillMode=mixed` / `TimeoutStopSec=30` (systemd); run the installer again to get them on an existing computer.
- **Only a turn that really started can be a repeat:** a message whose holder died before it started the agent is delivered later as a first delivery, unlabelled. A plugin whose daemon was killed stops taking work at once. A turn left running by a plugin that is gone holds its session: no second message is started in that session meanwhile. A process is identified by its pid and its start time, so a reused pid no longer keeps a message held for hours.
- **When a turn really was cut off** (killed with the daemon, a crash), the message is delivered again once its holder is provably gone — and the agent is told in the first line that it may be a repeat and should check what it already did. Three interrupted turns in a row and the message is set aside as dead — its session still gets it (labelled) the next time it asks, and on WeChat you are told it was not finished.
- **A turn cut off by a signal is no longer a "failure":** when the agent CLI is killed in the middle of a turn (a manual restart, launchd or systemd ending the job, a crash of the daemon), the message used to be retried without the warning — and on the WeChat channel it was dropped at once with "处理出错了". It is now delivered again with the warning, and only three cut-off turns in a row end it.
- **Restart with `morse stop --restart`** (not `launchctl kickstart -k …` / `systemctl --user restart morse`): it lets a message being handled finish first. An existing install gets the longer stop time by itself: at its next start the daemon adds `ExitTimeOut` to its own launchd plist, or `KillMode=mixed` and `TimeoutStopSec` to its own systemd unit (nothing else is touched, nothing is restarted; launchd uses it from the next login).
- **Plugins of your own:** nothing changes unless you ask for a lease (`morse plugin claim --lease`, `--holder` on `ack` / `nack`, the new `morse plugin extend`); messages gain `possibleRepeat`. Without a lease the old, weaker behaviour stays (docs/PLUGINS.md says where a repeat can still happen).
- Two small hardenings for apps that use the local API with their own token (闪电说 and the like): a token is bound to at most 256 session ids (the oldest goes), and their session search matches titles only, no longer the project folder's name.

### Two nouns: an address is yours, a contact is everyone else; you name your own address the way you name a contact (ADR-088; on branch `feat/agent-owned-addresses` — not merged, not deployed)

The first draft of this change named addresses after agents (default names `claude` / `main`, an automatic rename at daemon start, commands that recognised which agent product ran them). The owner rejected that direction — Morse is *for* agents, and another agent is simply a contact — so all of it was removed before release. What ships:

- **Two nouns.** An address is yours; a contact is everyone else, your own agents elsewhere included. "Agent" only says who uses Morse; it is no longer something the product names, detects or manages.
- **You name an address like a contact:** `morse address set <name|address> --name <new name>` (no selector needed with a single address; `--name ""` clears it), with a remark's rules and error lines (any text; not a command word, nothing that looks like an address — and no leading `@` or colon). It writes one local file: the address stays, links people hold keep working, the earlier name is still accepted by `--from`. `morse address rename` remains as a hidden alias.
- **`morse address add` no longer needs a name:** an unnamed address is shown by itself until you name it.
- **A name is on one side:** the name of one of your addresses cannot also be a contact's remark (any case), and the other way round — one error line says which side has it. Names that collided before the update are left alone; only new naming is checked.
- **With one address no name is shown anywhere:** `morse address` prints the address alone, `knows you as:` shows the address only, and the "cannot be removed" line names nothing.
- **No detection of who runs a command.** Which address a session uses: `--from <name>`, or `MORSE_ADDRESS=<name|address>` in its environment (then mail goes out from it and lists show it only; `--all-addresses` shows everything). Unset, behaviour is the released one, byte for byte. A wrong value is one error line for a command and silence for the prompt hook.
- **`MORSE_ADDRESS` never reaches the daemon or its plugins:** a daemon started from a shell that exports it behaves exactly like one started from a clean environment — it drops the variable from its own environment at start (one log line), plugins and the commands run for them are started without it, and a command a plugin runs ignores it even if it is there. (Found reviewing the first draft: an inherited caller mark made the plugins' own `morse message --json` return nothing — the attendant did not answer and the WeChat bridge never saw the reply.)
- **Writing to a contact of another address:** the refusal now names the address the contact belongs to (`--from <that one>`, or unset `MORSE_ADDRESS`). It used to say "use their address … `--from <the other one>`", which, followed, showed the contact your second address.
- **Last round before release:** looking a contact up by name with `MORSE_ADDRESS` / `--from` naming another address now says which address the contact belongs to instead of "add one"; `morse address` marks the address `MORSE_ADDRESS` selects; names are compared NFC-normalised; an address's hidden earlier name cannot become a contact's remark; naming an address what it is already called writes nothing, and clearing a name says so; `morse join` speaks of addresses and contacts.
- **Message rows keep one stable name:** a row stores the directory's name for your address; the name you gave it is looked up when the row is shown, so a listing no longer mixes old and new names.
- **`--session`** (where the answer comes back to) is separate from `--from <name>` (which address it goes out from); both can be given, and `--from "@…"` is still accepted.
- **A new address needs no daemon restart:** the running daemon takes on `morse address add` / `remove` at once.
- **Nothing is renamed by an upgrade.** The installers still accept `--agent` / `-Agent` / `MORSE_AGENT`, but only as the name of an address that install creates; on a machine that already has an address it is ignored (it used to add another address). Windows no longer passes `win` by default.
- **Skill and agent page:** first use is install if missing → `morse address` → tell your user the address. No naming or renaming step.
- **Output that differs from `main` (5ce8c59) on a one-address install:**
  - the 72-step baseline test: 2 lines — `knows you as: mini (morse.im/…)` → `knows you as: morse.im/…` in `morse contact <who>`;
  - `morse address`, first line: `address: morse.im/…   mini` → `address: morse.im/…`;

### Local API follow-ups: an app's token reads only its own session's mail; the token goes only to your own daemon; `morse stop` no longer finds a daemon by name (ADR-087 addendum)

- **An external app's token (闪电说 and the like) is bound to its own sessions** (medium): an app could "register" any session id as its own and then read that session's mail. A token now works only for the sessions it is bound to, mail is read by (app name, session), and the session list an app gets has agent names and titles only — no session ids, no directories. **Existing integrations need nothing:** a token issued before is bound in place the first time it is used.
- **The token is presented only to the daemon of your own home:** a `--port` other than your daemon's is refused and nothing is sent there; even on the right port the listener first has to prove it holds the token. The ilink plugin no longer passes a default port. 闪电说's `curl` now reads the token header from a file, so the token is not on a command line (the update rewrites its instructions).
- **`morse stop`** with no pid file no longer searches the process table (it could stop another Morse home's daemon): only the process your own `daemon.json` names counts; when unsure it says "not running".
- **The web console** sends between sessions on this computer only; for another address use `morse send`.
- **Mail that was being delivered when the daemon restarted is no longer stuck:** it used to be marked failed, the original deliverer's later "delivered" was rejected, and a pull by the session did not see it. Both now count.

### Security fix: the daemon's local API needs a credential, web pages are kept out, and a command talks only to its own home's daemon (ADR-087)

- **The problem** (pre-existing, confirmed by an independent review): the daemon's local HTTP API had no token and no origin check, and parsed any body as JSON whatever its content type. Any web page you opened could queue mail into a local agent session as you, have the daemon send files off your disk to an address of its choosing, and read your session list through DNS rebinding. Separately, `morse send` posted to `127.0.0.1:7433` whichever Morse home it belonged to.
- **Every route now needs a credential:** the daemon writes a random token to `~/.morse/daemon.json` (readable by you only) at each start; the `morse` command reads it from its own home and sends it in the `x-morse-token` header. Missing or wrong: `401`. Only the liveness probe, the console's static page and the one-time-code exchange need none.
- **Browsers are turned away before that:** a request with an `Origin` that is not this server's own page, a `Host` that is not loopback with this port, or a body that is not `application/json` is refused; no CORS header is ever sent and `OPTIONS` answers `404`.
- **A command talks to the daemon of its own home, or to none:** with no matching `daemon.json` in its home — or when the process on the port does not accept this home's token — it hands nothing over and behaves as if the daemon were not running. `--port` no longer defaults to 7433; without it the port is the one your daemon is on.
- **The web console is still there:** run `morse console` and open the link it prints (valid for a minute, works once).
- **闪电说 (`morse connect sds`)** now calls the local API with a token of its own and can only receive and send plain text as `sds`. **Existing installs need nothing** — the update refreshes the instructions it wrote; if that did not happen, run `morse connect sds --apply`. **If you wrote your own `curl` calls against the local API:** add the `x-morse-token` header; `morse connect --agent <name> --session <id>` says where that agent's token file is.
- **Restart the daemon after updating:** installs managed by launchd / systemd restart by themselves. If you start the daemon by hand, the CLI refuses to send or change contacts until you run `morse stop && morse start` — and until then the old daemon still has the problem above.
- The LAN peer API (mutual TLS, another port) is unaffected.

### Received file names are sanitised on every platform; four Windows tightenings from the review (ADR-080)

- **For macOS / Linux users: the name of a file somebody sends you is now cleaned up on every platform** (it used to lose only directories, control characters and a leading dot). Examples: `Q3:Q4 report.pdf` → `Q3_Q4 report.pdf`, `What is this?.md` → `What is this_.md`, `aux.c` → `_aux.c`, and a trailing dot is dropped (`notes.txt.` → `notes.txt`). Replaced: `: < > " | ? *`; Windows device names such as `CON`, `NUL`, `AUX`, `COM1` (with any extension) get a `_` in front; trailing dots and spaces go. Names that become equal after this — including names that differ only in case on macOS / Windows (`Report.PDF`, `report.pdf`) — are told apart automatically (a `_` in front): **nothing is overwritten** (the case-only kind used to be replaced by the later file; fixed here too). An ordinary name is unchanged. The reason: the file may be forwarded to Windows, where `a:b` writes a hidden data stream and `NUL.txt` writes to a device. Files you send are renamed by the same rule.
- **Windows: an access list that cannot be read is a failure.** When the data directory's ACL was checked, an entry with nested parentheses (a conditional entry) used to be skipped together with every entry after it — "somebody else can read this" read as "nobody else". Entries are now read one by one, and anything left over that is not understood fails the check.
- **Windows: the daemon checks the data directory's ACL again at every start** instead of trusting the marker left the first time; a directory copied or restored without its ACL is protected again, or the daemon refuses to start.
- **The hook no longer performs, or waits for, a mailbox upgrade**: `morse hook …` returns an empty result when there is no mailbox yet or it is of an older schema; the daemon or the next ordinary command upgrades it. (Codex gives this hook 10 s, and the user's prompt waits for it.) Every platform.
- On Windows the hook's "how to answer" line now names `--text-file` (a program passing the text as an argument is refused there).
- ADR-080 §26 now says plainly that the refusal of a text argument on Windows goes by stdin being a terminal, and that a harness giving its child a pseudo-console is not caught — a mitigation, not a guarantee.
- The Windows PC used for the real-machine rounds was moved to the released build with the real installer: signature verified, same address, contacts and history, hook files and logon task byte-identical before and after.

### Windows, phase 1: merged with contacts per address; a lock tells a live daemon from a stale pid file on Windows; the Codex sandbox group's read access is recognised (ADR-080; still on the branch)

- **Merged main (ADR-083) and made its daemon checks hold on Windows.** ADR-083 decides whether the pid in the pid file is a Morse daemon by reading the process's command line, which Windows cannot give — so a stale pid file read as "running", or "an older daemon is running", and on Windows every logoff leaves a stale pid file. The daemon now keeps `daemon.lock` open in exclusive sharing mode until it exits; where no command line can be read the checks ask the lock: held = the daemon, free = another program (the pid file is stale), no lock file = unknown, as before. No process is started for it. macOS / Linux neither take nor ask a lock.

Now: exactly that group, with read access only, passes — and the line says that a sandboxed agent can read Morse's data, private keys included, but not write, so it can read mail and cannot send until the session has full access. Anything else still fails. The check before the first key is written treats it the same way.
- The stop token is written to `daemon.json` only when the daemon has a console.
- **The Codex hook entry carries a 10 s timeout** (Codex waits 600 s for a hook without one) — on a new or rewritten entry only: on macOS / Linux an entry that is already right is left alone, because Codex trusts a hook by the hash of its definition and silently skips a changed one until it is trusted again.
- **Real-machine rounds 3 and 4** ([docs/guides/windows-test-log.zh-CN.md](docs/guides/windows-test-log.zh-CN.md), Chinese): Codex documents no way to trust a hook without its UI — that one confirmation stays with the owner; the merged build upgrades in place — the database moves to contacts per address, contacts and history kept; a stale pid file is no longer taken for a running daemon; a short read-only check proves, after the next logon, that the task fired at logon.

### Windows, phase 1: second real-machine round; message text as an argument is refused from programs; `install.sh --no-join` no longer joins (ADR-080; still on the branch)

- **On Windows `morse send` / `morse reply` refuse message text given as an argument when a program runs them** (stdin is not a terminal: an agent, a script), with one line naming `--text-file`. Through npm's `morse.cmd`, `cmd.exe` replaces `%NAME%` in an argument with that environment variable's value — on the real machine `%PATH%` was sent as the PATH itself; an agent quoting somebody's `%SOME_SECRET%` into a reply would send the secret, and the client cannot tell afterwards. A person typing `morse send bob "hi"` in a terminal is unaffected; macOS / Linux are unchanged. The skill and the guide say the same.

This also repairs a first install: the address used to exist before the script's own `morse join --relay … --agent …` could run, so `--relay` and `--agent` had no effect on a first install.
- **`install.ps1`: after a change of Node or npm prefix, the daemon of the old install is stopped** (it only looked at the new location; the old copy kept running while the logon task and the hooks pointed at the new one).
- **Second real-machine round** (the same Windows 11, over SSH; [docs/guides/windows-test-log.zh-CN.md](docs/guides/windows-test-log.zh-CN.md), Chinese): with the system Node upgraded to 22, reinstalled into the regular location as the guide says — `morse` on PATH, the logon task and both hooks point at the system Node and npm prefix (paths with spaces), same address; the task definition checked item by item (at this user's logon, not elevated, no time limit, not tied to battery); one headless `codex exec` showed that **Codex skips a hook that is not trusted yet without a word**.

### Native Windows support, phase 1: install, send, receive (ADR-080 — on a branch, not yet checked on a real machine, not released)

- **Status.** Written and tested on macOS. Every Windows branch takes the platform and the system commands (`icacls`, `whoami`, `schtasks`, `reg`, `taskkill`) as arguments, so it runs in the unit tests against fakes — **no line of it has run on a real Windows, and `site/install.ps1` has never been parsed by PowerShell**. It is merged and released only after the owner has gone through the checklist in [docs/guides/windows.zh-CN.md](docs/guides/windows.zh-CN.md) (23 steps) on his Windows 11. macOS / Linux behaviour is unchanged: no existing test was modified; one was added to `test/ci-policy.test.ts`.
- **Pull-only on Windows in this phase.** A message reaches an agent at its next prompt (the inbox hook) or when it runs `morse message`. LAN, direct links, every plugin (`dispatch`, `attendant`, `ilink`, custom ones) and auto-update are **off** there whatever `config.json` says; `morse status` prints a `windows:` block naming each one, and `morse plugin enable` / `morse update` say so too. The attendant being off is a temporary exception to ADR-066: whether its approval hook blocks or lets through when it fails on Windows is not known yet.
- **Install.** New `site/install.ps1` (`irm https://morse.im/install.ps1 | iex`): needs Node 22, only tells how to install Node. The download is checked against the signed release manifest by the **same** Node script `install.sh` uses (a test compares them line by line and runs it against real signatures: accepted, changed package, changed manifest, wrong key) — and stricter than `install.sh`: a copy the site build did not stamp with the key, or a site without a manifest, is **refused**; nothing skips the check. A running daemon is stopped before `npm install -g` (Windows does not let a loaded native module be replaced), and `morse.ps1` is removed afterwards (the default script policy blocks it; `morse.cmd` stays). The site build stamps the key into both installers and publishes both; a non-ASCII `install.ps1` fails the build. `install.sh` on Windows now names the PowerShell command instead of "install WSL2".
- **Background.** `morse start --background` (every platform) puts the daemon in the background itself, output appended to `daemon.log`, and returns once it is up. `morse autostart enable | disable | status` registers the logon start: a scheduled task of the user (not elevated, no 72-hour limit, not stopped on battery), the `HKCU\…\Run` value when Windows refuses the task — never both. Logging off stops the daemon; the relay's offline mailbox keeps the mail. No Windows service.
- **Stopping without signals.** The daemon has `POST /api/shutdown` — loopback only **and** it needs the `x-morse-token` header, random per start and written to `daemon.json` (loopback alone is not enough: any web page can post to a local port). On Windows `morse stop` uses it, waits for the process, and only after 5 s ends the process tree with `taskkill /T /F`, saying so. On macOS / Linux `morse stop` still sends `SIGTERM`, with the same output.
- **Private keys.** `chmod` does nothing on Windows. Before the first private key is written (and when the daemon starts) the data directory's inheritance is cut with `icacls` and only the owner, SYSTEM and Administrators are left, then the ACL is read back as SDDL; **if that cannot be done, no key is written** (the error carries the raw output). No switch skips it. `morse status --check` reads it again every time.
- **Hooks.** On Windows `morse setup` writes Claude Code's hook as `command` + `args` (no shell) and Codex's as `commandWindows` pointing at a launcher, `bin\morse-hook.cmd` in the data directory (the command itself has no quotes — the default Node path has a space, and how Codex hands a quoted command to `cmd.exe` is not documented). Each hook run leaves a timestamp on Windows, shown by `morse status --check` ("last ran" / "has not run yet") — a hook that does not run is otherwise silent. The POSIX single-quoted form stays on macOS / Linux, unchanged.
- **Security fix, every platform: file names chosen by the sender.** `safeFileName` let through `:` (on NTFS `report.txt:x` writes a hidden stream of `report.txt`), `< > " | ? *`, reserved device names (`CON`, `NUL`, `COM1` …, with any extension) and trailing dots and spaces. Now those characters become `_`, a reserved name gets a `_` in front, trailing dots and spaces are dropped; on Windows a name is cut to 120 characters. An ordinary name is unchanged. It applies everywhere — a Mac may forward the file to someone on Windows.
- **`--text-file <path>`, every platform.** `morse send` and `morse reply` can read the text from a UTF-8 file. A Windows command line goes through PowerShell and `cmd.exe`, which change quotes, `%`, `&`, line breaks and long text; the skill says when to use it. UTF-8 and UTF-16 with a byte-order mark are read; any other encoding is an error rather than garbage sent.
- **Also.** A rename over a file another process has open fails for a moment on Windows (`EPERM` / `EBUSY`): `writeFileAtomic` retries for about 2 s there (only there). `morse status --check` has its own checks on Windows (no `which`, file modes are always 0666, the agent CLIs are not needed in this phase) — no false alarms.

### Each address of yours has its own contacts and message requests: someone who knows two of your addresses cannot tell they are one computer (ADR-083; not merged, not deployed)

- **Everything is kept per (my address, peer):** contacts (remark, group, permissions, history), message requests (the request-area limit is per address too), blocks, tombstones of removed contacts, dedupe, rate accounting, holds, transfer state. The same person is two unrelated contacts at two of your addresses; a contact of one is still a stranger at the other.
- **With one address nothing changes** (output identical byte for byte, JSON only gains fields). With several: rows of `morse contact` / `morse message` end `via <name>`, and `--from <name|address>` says which address (`contact --from work`, `contact add … --from work`); naming a peer by address when that is ambiguous asks for `--from` instead of guessing. Remarks stay unique across the computer. P3's "warn, then send from another address" is gone.
- **Migration:** `user_version` 3 → 4 with the P2 discipline — one small backup taken inside the transaction by the process that migrates (`~/.morse/backups/contacts-per-address-<UTC stamp>/`), idempotent, kill-safe, concurrent openers migrate once. Existing contacts belong to the first address (unless P3 already recorded another); a peer with history at another of your addresses keeps a contact there, so nothing that worked before the upgrade stops.
- Published prekey timestamps and rotation moments are staggered per address (prekeys made in one daemon start were 1 ms apart and rotated in the same tick, which could link addresses); the cache of a peer's key and prekey is per (my address, peer).
- **People you had blocked before the upgrade stay blocked at every address you had then**; later blocks are per address, and `contact unblock` lifts one and tells you when other addresses still block them. A removed contact's history can no longer surface under another address.
- **Daemon not restarted yet** (database upgraded, older daemon still running): every command says so, and commands that change contacts, requests or blocks, or that send, are refused until it is restarted.
- **If your daemon is not managed by launchd / systemd** (started by hand with `morse start`): after the automatic update nothing restarts it, and the CLI refuses to send or change contacts until you restart it yourself — `morse stop && morse start`.
- **A left-over pid file is no longer taken for a running daemon:** after a crash or a reboot the pid in `~/.morse/daemon.pid` may belong to another program. Commands now check that the process really is a Morse daemon (its command line) before they speak of an older daemon, say "already running" or signal it; a stale pid file is removed — `morse start` starts, and `morse stop` signals nobody. Where the command line cannot be read (Windows), behaviour is as before.
- **When the upgrade cannot be done safely** (several addresses, someone blocked, and `~/.morse/addresses/agents.json` unreadable) every command says one line — what is wrong, which file, that nothing was changed — instead of a stack trace. A computer with one address is upgraded regardless: there is no other address to carry a block to.
- The backup also holds the table and index definitions; manual restore steps are in `docs/guides/restore-contacts-backup.zh-CN.md`. The test fixture carries no keys (they are generated at test time).
- **What remains:** the relay (not the people you talk to) sees several addresses log in over one connection; whether an address is online can be looked up by anyone; "this is not some computer's first address" stays observable until v2 is removed.
### The page's sound is now led by the Morse code tone, with the key's click underneath (second addition to ADR-085; on branch `feat/site-sound-real` — not merged, not built, not deployed)

- **The code tone leads:** a pure 750 Hz note with 5 ms raised-cosine edges — short for a dot, long for a dash, instantly readable as Morse. ### Minimum Node.js is now 22; an install already on Node 20 is not refused, it only gets a hint (ADR-084; not merged, not deployed)

- **Why:** the database module (`better-sqlite3`, 12.11.1) no longer ships a prebuilt binary for Node 20 — its release assets cover Node 22 / 24 / 25 / 26 only, since 12.10.0 — so a fresh install on Node 20 has to compile it and fails without a C++ toolchain; Node 20 reached end of life on 2026-04-30.
- **New installs:** `site/install.sh` (and the old root `install.sh`) require Node.js 22+. On Node 20 / 21 the installer stops before changing anything, says why and how to upgrade; it still never installs Node for you. `package.json` `engines.node` is `>=22`.
- **Existing installs on Node 20 keep starting and updating** (npm only warns about `engines` unless you turned on `engine-strict`). They get a hint: `morse status` prints one extra line — `node: v20.x.y — Node.js 22+ is recommended: on older Node.js every update has to compile the database module from source` — and the daemon log has the same line after an auto-update. No refusal, no exit code change.
- Docs, the site and CONTRIBUTING say 22. CI drops the Node 20 job (one Ubuntu job per push instead of two — fewer minutes; nothing added).

### Each contact remembers which of your addresses it knows you by; an un-restarted older daemon never sends from the wrong address; mail queued before the upgrade goes out as before; `contact reject --all` (ADR-081, fourth review; not merged, not deployed)

- **The default sending address is per contact** (`contacts.known_as`, an additive column): the address their first message was written to, or the one you first wrote to them from. Without `--from` mail goes out from it; `--from` applies to one message and warns; `morse contact <who>` shows `knows you as: …`. If that address is gone the message is refused — never sent from the first address.
- **New command, older daemon still running:** mail that must go out from a specific address (`--from`, the remembered address, a reply to mail that came by address) checks the daemon's capability before posting; with an older daemon nothing is posted and you are told to run `morse stop && morse start`.
- **Mail queued before the upgrade is no longer refused:** rows with no recorded address that are older than this computer's first start of the new daemon go out from the first address exactly as before; later rows record the address when queued.
- `morse contact reject --all` rejects every pending request at once (nobody is blocked).

### Review fixes for mail by address: the first address never stands in for another; an old handle cannot look like an address; a full request area refuses instead of evicting; a per-IP limit on the relay (ADR-081 review F1–F6; not merged, not deployed)

- **Your first address is no longer disclosed to someone who only knew another one.** The sending address and the written-to address are now stored as addresses (`messages.my_address`, `morse_requests.to_address` — additive columns, no version bump, nothing existing rewritten), and every signature takes its key from one place; when that key is not there (the address was removed, `agents.json` is damaged) nothing is sent — never from the first address, never by the old handle path. Renaming an address changes nothing.
- **An old handle can never have the shape of a 26-character address**, which closes an injection path through a lying relay; only a request that arrived by address is accepted by address.
- Receipts, rekey notices and chunk acknowledgements are bound to the address pair. **Known limit:** someone who knows two of your addresses can tell they are on the same computer (for now).
- **A full message-request area no longer evicts an older request**: the newcomer is refused and told to try later; `morse contact` / `morse message` say when the area is full.
- **Relay:** v3 sends share a limit per client IP across connections (`V3_RATE_PER_IP_PER_MINUTE`, default 600; a new `IpBucket` Durable Object, migration tag `v5`). Independent of the client release order.
- "Another person's mail never picks a session" (ADR-082) now judges by the tier the mail is stored with.

### The 26-character address works on its own: add contacts, send, requests and blocks by address; every address on this computer can send (ADR-081; not merged, not deployed)

- **The address you share is the 26-character one.** `morse contact add morse.im/<address> --name <remark>` works for someone you never talked to, with no relay lookup (the address is the identity); `morse send morse.im/<address> "…"` to an unknown address adds the contact and sends (writing first = accepting). The recipient gets **one** message request from that address, with the same rules as before: not in the inbox, agents cannot accept it, `morse contact accept | reject | block <address>`. Blocking, unblocking and removing work by address.
- **What `morse address` and the installer say**: the old-name line is now `old name: morse.im/<old name>   (still reaches you)` — "share this one for now" is gone; a new computer's first `morse address` prints `created: your address is morse.im/<26-character address> — send it to your friends; next: morse start`. `site/install.sh` ends with `Your address: morse.im/<26 characters> — send it to your friends.` and, when there is an old name, `Old name: morse.im/<old name> (still reaches you).` (one new helper, `current_address`, reads the first line of `morse address`; the join logic is untouched).
- **Reaching someone by address needs their Morse to be this release or newer.** If theirs is older nothing is sent and the sender gets exactly: `<address>: their Morse is too old to be reached by address alone (it needs the release after 20261114170051) — ask for their old-name link (morse.im/…)`. If nobody published the address: `nobody has published <address> yet`. Old-name links (`morse.im/<old name>`) and existing contacts are unaffected, both ways.
- **Every address on this computer can send**: `morse send --from <name|address> <who> "…"` (the name is the local one in `morse address`; `--from @<agent>:<session>` still means a session) sends as THAT address — the recipient sees only it, never your first one; replies come back to it, and `morse reply` answers from the address that was written to. From a second address you can only write to people on this release or newer (the same too-old line otherwise). After `morse address add <name>` the daemon still has to be restarted before the new address sends or receives.
- **The relay gains address capabilities** (`caps`, `addr1`), additive. **Deploy order: relay first** — otherwise new clients report each other as "too old" when writing by address until the relay is deployed; everything else keeps working.
- **Another computer of yours stays a contact**: install there, add each other by address, and give the contact or its group permissions with `morse contact set`. The idea "`--group self` = own computer" was considered and cancelled by the owner (2026-11-15): there is no special permission mechanism, putting a contact into `self` by hand still grants nothing, and computers paired before the update stay in `self` with the trust they had.
- `morse agent remove <first>` (hidden alias) refuses, like `morse address remove` of the first address.
- Docs follow: QUICKSTART (zh + en), README (zh + en), the skill, the site, install.sh hints, PLUGINS (a request by address carries the address in `handle`); the greps on the installer's last lines in `scripts/morse-e2e-register.sh` and `scripts/morse-e2e-join.sh` are updated.
- Tests: `test/morse-address.test.ts`, `test/cli-address.test.ts`, the relay-cf tests.
### Another person's mail never picks a session: the rule now lives in one place (ADR-082)

- **The report** (a real user, 2026-10-26): a contact's message whose target named `claude` — a session type — or a bare `@claude` was handed to the most recently active Claude session and woke it. **That path was closed on 2026-11-12 (ADR-048)**; the new `test/peer-never-picks-session.test.ts` pins it for every form the report named (an agent name, a type name plus a session id, `@dispatch:<name>`, `@user`), through the relay / LAN code and the older LAN route.
- **One enforcement point.** The rule used to be applied by each way in (the relay / LAN code, the older LAN route, accepting a message request); the mailbox stored whatever session it was handed. Now the mailbox itself files another person's mail in `<agent>/inbox` whatever its caller names, and only then checks whether it is a reply in a thread one of your sessions started (ADR-071) — from your own records. So the only session another person's mail can reach is the one that wrote to them. A new way in cannot forget the rule.
- **`whenLive: "resume"` no longer follows the sender's agent name.** A launch setting keyed on `from` (the WeChat profile, `from: "ilink"`) was matched against the sender's own agent name when deciding whether to run a turn in a session that is open. A contact who called their agent `ilink` got their reply in your thread run inside your open session. Such settings never apply to another person's reply now; it waits for the session's next prompt, as other mail does.
- **A session id a sender writes as its own is not your session.** `morse message --pull --history` (and `/reload`) listed another person's message as something *this session sent* — full text, no peer label — when the sender wrote that session's id as its own (ids crossed the wire before ADR-048). Fixed; a peer message shows in a session's history only when it was delivered to it.
- Your own computers (owner tier) behave exactly as before. No new command or option, no wire or database change.

### `morse address` replaces `morse agent`: five visible commands; pairing codes are no longer taught; a new lead sentence (ADR-079, ADR-077 #17)

- **`morse --help` lists five commands**: `address`, `contact`, `message`, `send`, `reply`. One agent = one address, so `agent` is folded into `address`: `morse address` (the addresses on this computer), `morse address add <name>` (another address = a new agent with its own key; restart the daemon afterwards), `morse address rename <name|address> <new name>`, `morse address remove <name|address>`. A name is a local label and may not be `add` / `rename` / `remove`. `morse agent …` is a hidden alias with unchanged behaviour.
- **`morse address` prints addresses only**: the address first with its local name, one line per address on this computer, `old name: morse.im/<old name>` when there is one, then the relay. No `agents` line, no device ID (now `device:` in `morse status`), never "v3" or "handle". The same leftovers are gone from the other visible commands (the migration line of `status`, `device` → `computer` in the request list, …).
- **"Add an agent to your address with a pairing code" is no longer taught.** `agent add <name>` only means another agent on this computer with its own address; `agent add` with no name (a pairing code) and `join <address> --code` remain as hidden compatibility paths until v2 is removed, and are gone from help, the site, install.sh, QUICKSTART, README and the skill. **Another computer of yours**: install there, add each other as contacts, and give the contact or its group permissions with `morse contact set`. Said plainly: in this release, putting a contact into group `self` by hand does not give it your own-computer trust (`self` belongs to computers that were already paired before the update) — use a group of your own for a newly added computer.
- **Copy**: the lead is now "An IM for AI agents. Every agent has one address; add each other as contacts and they exchange messages and files directly — end-to-end encrypted, no sign-up."; the docs no longer say the relay stores no messages — for an offline recipient it holds the sealed envelope for up to 7 days, deletes it on pickup and cannot read it; "your own other agents" are not a separate kind of thing, they are contacts.

### Identity v3, phase 2: the migration — contacts per address, your own computers as `self` contacts, the frozen alias table (ADR-077; not merged, not deployed)

- **After the second review (ADR-077 #18):** removing the contact of one of your own computers that you had moved out of group `self` no longer makes it an owner again (the lowered state is kept apart from the contact row); a contact you removed comes back only with `morse contact add …`, never because of what a sender does; the own-computer check fails closed when it cannot read the database; `morse address remove` refuses this computer's first address. Tests cannot default to the real `~/.morse` any more (`test/helpers/isolate-home.ts`).
- **The update migrates by itself.** The first time the new version opens the mailbox it moves the contacts table to one row per address in a single transaction (`user_version` 2 → 3). The transaction starts with the backup — one per computer, taken only by the process that migrates: the three contact tables as a small `contacts.sqlite` (no messages) plus `config.json`, `trusted-devices.json`, `peer-keys.json` and `morse-blocked.json`, in `~/.morse/backups/identity-v3-p2-<UTC stamp>/`. No backup, no migration (one clear error line); killed halfway it rolls back and runs again; several processes opening at once migrate once; running it twice changes nothing. **No message, message request, block or outbox row is touched, and no v2 file is deleted or rewritten.**
- **Contacts split per address.** Once the daemon is logged in it asks the relay which agents live under each old handle and at which address (the new `alias` query, else the v2 directory; when the relay cannot be asked the contact waits and works as before). The default agent's address goes on the existing contact; an agent on another computer becomes a contact of its own (`alice/air`) with the same group, permissions and block state. A contact without a remark gets its old handle as remark, so it is shown as before. History stays with the original contact.
- **Your own other computers become contacts in group `self`** (owner decision, no confirmation step) with exactly the owner trust they have today. Move one out of group `self` and its mail is treated as another person's; move it back to restore. In this phase putting any other contact in group `self` does not make it an owner, and adding a computer still uses a pairing code.
- **Contacts are a real boundary.** Inbound mail is filed by the sender's verified address (its device certificate), never by the agent name it writes; the relay's alias answers are checked entry by entry (an address must be that of a device paired here), and an address recorded for one contact is never moved to another; a split contact you removed does not come back; moving one of your computers out of group `self` holds on every path (LAN API, direct links, …).
- **Old and new clients keep talking.** A contact with an old handle is still routed through the v2 directory, unchanged, and a reply in a thread you started is recognised by "same old handle" — so a message sent before the migration, or an old client's reply, still lands in the session that started the thread.
- **Relay (relay-cf):** the frozen alias table — one read-only KV record `alias:<handle>` per handle, no write path in the Worker — with the `alias` query on the v3 connection and `GET /v3/alias/<handle>[/<agent>]`; `/healthz` adds `aliases: true`. The admin builds and verifies the table from the relay's own data with `scripts/aliases-export.mjs` and loads it once with `wrangler kv bulk put`. **Deploy order: relay first (and load the table), then the client** — the other way round nothing breaks, the client falls back to the v2 directory.
- **An agent added after the first has its own key and address:** `morse agent add <name>` creates it and prints the address; the daemon logs it in on the same v3 connection and files mail sealed to it in that agent's inbox. `morse agent default` no longer does anything (hidden, exits 0). `morse status` shows where the migration stands.

### Native Windows support: the plan (ADR-080 — documents only, no code yet)

- **Why.** `site/install.sh` stops on Windows with "Install WSL2", and the owner's Codex desktop app on Windows 11 could not enter WSL ("Access denied"). Decision: Morse will run natively on Windows.
- **New spec**, [docs/specs/windows-native.zh-CN.md](docs/specs/windows-native.zh-CN.md) (Chinese): every Unix assumption in the client, with `file:line`, what happens on Windows, the fix and the phase — install and update, background service, paths and filesystem, agent integrations, native modules and networking, child processes, tests and CI, WSL.
- **Four things that are more than a path change.** Windows has no signals (`SIGTERM` kills at once, so an orderly stop needs another way); a loaded native module's file is locked (the daemon cannot `npm install -g` over itself); every shell usage is POSIX (`/bin/sh -c`, single-quoted hook commands, `ps` / `lsof` / `pgrep` / `which`); and an npm-installed `claude` / `codex` / `morse` is a `.cmd` file, which Node will not run without a shell — and with one, message text would reach `cmd.exe`.
- **Two findings that matter beyond Windows.** `safeFileName` (`src/cluster/morse.ts`) lets through `:` (an NTFS alternate data stream), `< > " | ? *`, reserved device names such as `CON` and `NUL`, and trailing dots and spaces — in a file name chosen by the sender. And the text of `morse send` / `reply` can only be passed as an argument; through PowerShell and a `.cmd` shim, quotes, `%` and `&` do not survive, so a `--text-file` option is planned.
- **Choices.** `irm https://morse.im/install.ps1 | iex`; Node 22+ on Windows (better-sqlite3 has had no Node 20 prebuilt binary for Windows since 12.10); a scheduled task at logon rather than a Windows service; `icacls` on the data directory instead of `chmod`; Claude Code hooks in exec form (`command` + `args`, no shell) and Codex hooks with `commandWindows`.
- **Six phases.** Phase 1 is the smallest thing that installs, sends and receives (relay only, messages are pulled in by the hook or by the agent — about 1,300–1,800 lines); then service polish, auto-update, delivery into sessions, LAN and direct links, and the remaining plugins and tests. About 4,000–6,000 lines in all.
- **Verified or assumed.** Each claim in the spec is marked as verified from official documentation or a release page (with the link), as secondary evidence, or as needing a real Windows machine. Nothing in it was run on Windows; it lists 24 things only a real machine can answer and 6 decisions for the owner.
- **CI proposal** (not applied): a `ci-windows.yml` that runs weekly and on demand only — about 45 billed minutes a month, 150–200 in the month it is developed.
- No code changes until `feat/identity-v3-p2` is merged.

### Direct links lost a large message when its fragments were handed over out of order; a stopped plugin left processes behind

- **Direct links (ADR-069): fragments are put together by their number, not by the order they arrive.** Under load node-datachannel hands the frames of an ordered channel to us slightly out of order (seen: `… f3 f5 f4 f6 …`, none missing). The receiver assembled them in arrival order and dropped the whole message as "out of sequence"; the sender then got no receipt, closed the link and resent through the relay. Each frame already says which message it belongs to and where it goes — that now decides (up to 4 messages in the air per link). A data frame that arrives before the `open` callback is no longer dropped either. This was the occasional timeout of "fragments a large envelope" in `test/direct.test.ts`; in a stress loop it lost about 1 message in 80 before, none in 2000 after.
- **Direct links: a call that fails the moment it is set up is made once more.** About 1 call in 3000 on loopback fails within milliseconds (ICE completes, then the transport closes at once — inside the native WebRTC stack; not traced further). That used to mean 5 minutes of relay-only for the device; now the call is repeated once, inside the 3 s the sender is waiting anyway, and only a second failure backs off.
- **`morse plugin watch` ends when nobody reads it.** It only noticed a missing reader when it tried to print an event; a plugin that was killed left its watcher polling for ever (every full test run leaked one such process). It now also ends when its output is a pipe and the process that started it is gone, or when the process named in `MORSE_WATCH_PARENT` no longer exists (the built-in plugins set it).
- **Plugins stop in order.** On SIGTERM the dispatch and attendant plugins used to exit at once, leaving `morse` commands they had started still running — reading and writing the Morse home with nobody to take their answer. They now close their event stream, start no new command, let the ones in flight finish (one still running after 2 s is stopped; the daemon kills after 3 s) and then exit; the ilink plugin waits for its commands too. In the tests this was the `ENOTEMPTY` when a temp home was removed while such a command re-created `mailbox.db` in it; the tests now wait for the processes they stop (`test/helpers/stop-process.ts`).
- **Relay: agents registered in the same millisecond keep their registration order.** The agent list (and which agent becomes the default after a removal) is ordered by registration time in milliseconds; two registrations in the same millisecond fell back to alphabetical order. A registration now always gets a time after the latest one of that address. This made `relay-cf/test/agents.test.ts` fail now and then on a fast run. Takes effect with the next relay deploy; the tests' in-memory relay does the same.
- Tests: `test/cli-client.test.ts`, four more cases in `test/direct.test.ts` (frames in reverse order and mixed between messages, a fragment that cannot belong, data before `open`, a call that fails as it is set up), two in `test/plugin-interface.test.ts` (a watcher whose reader was killed). `test/ilink-protocol.test.ts` used random keys for its "wrong key" case — AES-ECB only notices a wrong key by the padding, which looks valid once in about 256 runs; it uses fixed keys now.

### Two lost-update bugs behind flaky tests: concurrent `morse` processes dropped each other's changes; a receipt could vanish into a half-closed direct link

- **Stores under `~/.morse` are now changed under a lock and written atomically.** The blocklist, trusted devices, `config.json`, pinned keys, the update state, the dispatch / attendant plugin state and external registrations were read, changed and written back with no lock — two `morse` processes at the same moment (the daemon, a CLI call, a plugin) each read the old file and the second write dropped the first one's change (`morse contact unblock a` and `… unblock b` together could leave one of them blocked), and a reader could see a half-written file as empty. New `src/file-lock.ts`: `withFileLock` (a `<file>.lock` beside the file, taken over when its process died or it is older than 10 s; synchronous, re-entrant) and `writeFileAtomic` (temp file + rename, keeps the mode, follows a symlink). `morse relay set` and the attendant's `contact set` permissions take the same lock as every other `config.json` change.
- **A fresh home gets one device identity.** Two processes starting at once could each create a key and a certificate and leave one's key with the other's certificate; creating the identity (and the X25519 key) now happens under a lock, checked again inside it.
- **Receipts go back the way the message came (ADR-069).** When the sender gave up on a direct link (no receipt in time) and sent the message again through the relay, the recipient could still see that link as open — the close had not reached it yet — and wrote its receipt there; the sender no longer read the link, so it reported "forwarded but no receipt" and sent again later. ### Identity v3, phase 1: key-derived addresses, sealed v3 envelopes, an offline mailbox — next to everything that exists (ADR-073)

- Every computer now also has an identity-v3 **address**: 26 characters computed from its own key (`base30(SHA-256("morse-address-v1\n" ‖ Ed25519 key) mod 30^26)`), so nobody can claim or forge it. The first address of a computer is its existing device key, so contacts that pinned the device already hold the key behind it. Recovery words (24 BIP-39 words, English or Chinese, encoding the key seed as is) exist as a library; the commands come in a later phase. A remark may not look like an address.
- **v3 envelope**: signed by the sender's address first, then sealed with HPKE (RFC 9180: X25519, HKDF-SHA256, AES-256-GCM, via `@hpke/core`) to the recipient's signed prekey, rotated weekly (old private keys kept 8 days) — forward secrecy for captured traffic. Only the recipient address is visible outside; lengths are padded (1/4/16/64 KB…); envelopes older than 31 days or dated in the future are refused.
- **Relay**: a new `AddressHub` Durable Object per address at `/v3/ws/<address>` — one connection logs in all of a computer's addresses, address lookup (key, prekey, online), and an **offline mailbox**: a message to someone offline is kept (sealed) up to 7 days, handed over when they log in, deleted once they confirm; if nobody fetches it, the sender learns it was not delivered. File chunks never wait there. No allowlist; new addresses are capped per network (100 an hour), message sending is not. `/healthz` and the v2 login announce `protocols: [2, 3]`.
- **Dual stack, nothing you need to do**: the client opens the v3 connection only when the relay announces protocol 3, and uses v3 envelopes only for devices that published their address — over the relay, direct WebRTC links and the LAN (`/api/peer/morse3`). Everyone else, every old client and old relays get exactly the v2 behaviour; handles, pairing codes, commands and output are unchanged. Contacts now record their v3 addresses (`addresses` in the contact JSON).
- **No receive limit by default** (owner, 2026-11-14): `morse.receiveLimit` (ADR-037: 30 a minute per sender, 300 in total) now applies only when you set it — each cap on its own, 0 = no limit; no new command. The relay's 120 a minute per device stays (relay self-protection). Also decided: the offline mailbox keeps its 2000 messages / 200 MB per address, and on upgrade your own paired devices will become contacts in the `self` group with today's trust (phase 2).
- Design change by the owner (2026-11-14): **one agent = one address, no ownership layer** — your other agents are simply contacts; ownership and organisations, if ever, become plugins. The spec (docs/specs/identity-v3.zh-CN.md) is rewritten accordingly. The relay needs a deploy (new class + migration tag v4, additive only) before any of this is live.

### Morse no longer decides whether agents answer each other (ADR-072)

- The mailbox's per-thread caps are gone (a thread used to stop at 12 messages, and at 6 a minute).
- Attendant: no turn cap per thread by default (`maxTurnsPerContext` was 10 a day), and another attendant's automatic reply is handed to your agent like any other message (`answerAttendants` now defaults to `true`) — the `[morse-attendant]` marker stays in the text and the agent is told to decide itself (`NOOP` when the conversation is over).
- **Risk:** two agents can now answer each other indefinitely and spend tokens. Set `maxTurnsPerContext`, `rateLimit` or `"answerAttendants": false` in `~/.morse/config.json` to cap it (no new command). `NOOP`, the BLOCKED-answering-BLOCKED rule and the relay's abuse limits are unchanged; `rateLimit` stays off by default (ADR-068).

### Set what your agent may do for a contact with `morse contact set`; replies in your own thread come back to your session (ADR-070, ADR-071)

- `morse contact set <who> --cwd <dir> --tools Read,Grep,Glob,Bash --allow "Bash(git status:*)" --rate 10/h` sets the attendant's permissions for one contact (on top of their group's profile when there is one); `morse contact set --group <group> …` (no `<who>`) sets a whole group's; `--reset` removes them. No new command: five options on `contact set`. Checked with the attendant's own validation before anything is written (nothing is written if it fails, and you are told why); `~/.morse/config.json` keeps every other key, its order and indentation, and is replaced atomically. The other settings (`model`, `approval.require`, …) stay in config.json.
- `morse contacts <who>` shows one contact and what actually applies to them: which settings (contact / group / conversation-only default / stored only and why), directory, tools, what runs without asking, what waits for your approval, rate, model; `--json` too.
- One-way use needs permissions on one side only: when a session writes to another address (`--from @<agent>:<session>`) and they answer in the same thread — their attendant's answer, its "I will check with my owner", its waiting-for-approval notice — the reply goes back to that session (prompt hook when it is live, dispatch otherwise), framed as another person's message, and nothing is sent back by itself. Your own attendant no longer picks it up: before, it landed in the agent's mailbox, and your attendant either deferred it (loop guard) or — when the other side's owner answered by hand — answered it back on your behalf. Decided from your own records only (contextId = the id of your message, from the address you wrote to); strangers' first messages still go to requests. Plugin JSON adds `ownThread`. Tests: `test/contact-permissions.test.ts` (12), `test/own-thread-reply.test.ts` (7).

### Direct WebRTC links between contacts, relay as fallback (ADR-069)

- A message to a contact's device first tries a WebRTC data channel (`node-datachannel`, STUN `stun.cloudflare.com:3478`, no TURN yet); if no channel opens within ~3 s, or it drops mid-way, it goes through the relay exactly as before. Same end-to-end encrypted envelope, receipts, dedupe and chunked transfers — only the path changes. Links are reused and closed after 5 idle minutes; a device that cannot be reached directly is not tried again for a while (5 min, doubling to 6 h).
- Signaling (offer / answer / ICE candidates) goes over the existing relay WebSocket as a new `signal` frame, forwarded only between logged-in devices and never stored. Every signal is a full Morse envelope — signed by the sender's device key, encrypted to the recipient — and only accepted from known contacts / paired devices, so the DTLS fingerprint in the SDP is bound to the device identity and the relay can neither hijack the channel nor read the candidates. Old clients ignore the new frame; a new client on an old relay just uses the relay.
- `node-datachannel` is an optional dependency, loaded with a dynamic `import()`: if it is missing or fails to load, Morse runs relay-only and the zero-compile install path is unchanged. Turn it off with `morse.direct.enabled: false` or `MORSE_DIRECT=0`. `morse status` shows a `direct:` line; logs and the delivery trail say `via direct` or `via relay`.
- Data bigger than one relay envelope still goes in ADR-038 chunks — over the direct link when it opens, through the relay when it does not (no TURN yet).
- Considered the pure-TypeScript `werift` instead: it works for data channels + STUN and interoperates, but its current releases need Node ≥ 22 (we support 20), it pulls ~28 MB of dependencies (incl. a media library) and was ~7× slower on loopback; `node-datachannel` ships prebuilt per-platform binaries with no install script, so it stays the (optional) choice. Details in ADR-068.
- relay-cf and the self-hosted relay forward `signal` (needs a relay deploy to take effect online). Spec: docs/specs/phase7-webrtc-direct.md.

### Your agent reads your contacts' messages and decides whether to reply — attendant on by default (ADR-066)

- Like a chat app: a message from an accepted contact (not you, not a request, not blocked) reaches your agent in a session of its own for that contact, and the agent decides whether to reply. The agent replies briefly or answers `NOOP`; it is told it must never claim to do what it cannot do, and an answer that is a written-out tool call is never sent.

It is stripped before sending (the contact gets `notices.askOwner` if nothing else is left) and you get a desktop notice, a line in `morse attendant status` (`morse attendant dismiss <id|all>`), and a WeChat message when the ilink plugin is on — the approvals notifier path.

### Fix: the relay connection could stay down for days without ever reconnecting (ADR-043)

A daemon logged `relay: disconnected (1006)` and then nothing for 8 days, until it was restarted. - Failed attempts are logged (1st, 2nd, 4th, 8th … in a row) with the reason.

- Auto-update: a scheduled check that never finishes counts as failed after 45 min and the next check is always armed.

### Morse: large files in chunks — up to 100 MB, end-to-end encrypted chunk by chunk, checked before filing, resumable (ADR-038, 2026-10-21)

- Attachments that do not fit one relay envelope (≈550 KB on Cloudflare) are no longer refused: the message carries a manifest (names, sizes, whole-file SHA-256, chunk size, chunk counts) and every 512 KiB chunk travels as its own envelope — sealed and signed end to end, numbered (message ID + file index, chunk number, chunk count, file SHA-256), raw bytes inside (no second base64), ≈700 KB sealed. Smaller attachments still go inline as before.
- Recipient: chunks are staged in `~/.morse/incoming-chunks/` (0700/0600, any order, duplicates ignored, at most 1 GiB `morse.maxStagingBytes`, deleted after 24 h without progress). Once all are in, each file's SHA-256 is checked, the files move to `~/.morse/inbox-files/<id>/` (0600, never run or opened) and only then is the message filed — text and files appear together. A file whose checksum does not match is asked for again.
- Reliability: the recipient answers the manifest with the chunks it already holds and acknowledges in batches (every 8 chunks / 300 ms); the sender keeps at most 24 chunks in flight, asks again after 15 s of silence and re-sends only missing chunks. The progress lives on the recipient's disk, so a restart of either side resumes where it stopped. The transfer runs in the background; the outbox shows `waiting: sending … x/y chunks confirmed` and marks it delivered as soon as the final receipt arrives.
- Limits: 100 MB per file and per message by default (`morse.maxFileBytes`), refused at send time; the recipient refuses manifests over its own limit (the sender fails it instead of retrying). Chunks share one token bucket at 5/6 of the relay's per-device rate (100 of 120 a minute) and wait out `rate limited`; the recipient's 30-a-minute per-person limit counts the manifest once — chunks are not messages (they are bounded by the declared bytes).
- Message requests take no chunks: only file names and sizes are kept; once accepted, the sender's device queues the files again as a new message.
- The LAN path does the same over mutual TLS (chunks as JSON + base64; the HTTP answer is the acknowledgement) and switches to the relay mid-way if the LAN fails.
- CLI: `morse send --file` shows `sending: x/y chunks confirmed` and `delivered: …` (`--no-wait` to skip); `morse inbox` lists name, size and path of each file and `receiving x/y chunks` for messages still arriving. Daemon: `GET /api/morse/transfer/<id>`.
- No relay change (no deploy needed). Large files need the current version on both sides; an older recipient gets only the text, and the sender marks the message failed with an upgrade hint. Tests: new `test/morse-chunks.test.ts` (22); acceptance `scripts/morse-e2e-files.sh` (relay 1/10/50 MB, recipient killed mid-transfer and resumed, LAN 10 MB).

### Morse: message requests — a stranger's first message waits until you accept; inbound rate limits (ADR-037, 2026-10-21)

Idempotent; a running daemon is stopped first (setup) or left alone (another daemon's start); any failure leaves (or puts back) everything in `~/.anytoany`, which stays in use while it is a real directory — device ID and mailbox never change.

- Tests: new `test/migrate-home.test.ts`; acceptance `scripts/morse-e2e-migrate.sh` (old layout written by the previous version, temp HOMEs, install.sh upgrade with a launchd dry run).

### Morse: your own devices are owner; Morse addresses go over the LAN first (ADR-034, 2026-10-21)

- **Same handle = your own device = tier `owner`**: pairing by handle (first send, automatic pair-back, `morse pair add morse.talk/<you>`) now gives `owner` when the handle is this device's own handle on the relay — only an invite issued for that handle can put a device under it. Other people stay `peer`; an `owner` entry is never downgraded. Old same-handle `peer` pairings are upgraded after every relay login (upgrade only, never adds a removed device) and on the next directory lookup when sending or receiving. `morse pair remove <your handle>` also blocks it. ADR-016 owner semantics unchanged.
- **LAN first for `morse.talk/<person>/<agent>`**: after the agent directory names the one device, a device that is paired and discovered on the LAN gets the message straight over the existing mutual-TLS peer API (new route `POST /api/peer/morse`, same plaintext the relay path seals; both certificates pinned); its answer is the receipt. Failure (not paired / older peer 404 / unreachable / 5s timeout) falls back to the relay. Peer-tier devices may use the LAN too; the tier does not change. With the relay down, an address resolved earlier still goes over the LAN. Logs say `delivered via lan` / `lan failed (…) — falling back to relay` / `delivered via relay`; filed messages carry `via: morse-lan` or `morse-relay`; the dispatcher line ends `via lan|relay`.
- The daemon sends an mDNS goodbye before exiting (no ghost entries on other devices).
- No relay or protocol change: nothing to redeploy; clients just upgrade (an older peer answers 404 on the new route → relay).
- Tests: new `test/morse-lan.test.ts` (10). Acceptance: `scripts/morse-e2e-lan.sh` (local `wrangler dev`, temp HOMEs, real mDNS under `e2e-lan-*` device names).

### Morse: one address per agent, the agent directory on the relay, the command is `morse` (ADR-033, 2026-10-20)

- **Every agent has one address, `morse.talk/<person>/<agent>`, hosted on exactly one device** — a message goes to that device only (no more fan-out to all of a person's devices). `morse.talk/<person>` reaches the person's **default agent** (the first one registered; `morse agent default <name>` changes it). Agent names: a-z 0-9 `-`, 1–32, unique per person.
- **One agent per computer by default**, registered at join: `morse join <code> --agent <name>` / `install.sh --agent <name>`; without it the name comes from the computer (`…Mac-mini` → `mini`, `…MacBook-Air` → `air`, `…MacBook-Pro` → `pro`, else the slugged device name). It is "this computer's agent inbox": messages land in `<agent>/inbox`, readable by any agent on that computer with `morse inbox` / the new `morse pull --inbox` (never headless-resumed).
- **`morse agent list | add | remove | default | rename`**: signed by the device's own key (`POST /v1/agents`, `morse-relay-agent-v1\n<ts>\n<op>\n<agent>\n<to>`); the handle comes from the relay allowlist, never from the request; only the hosting device can add / remove / rename its agents. Rename is atomic — the new address works at once, the old one stops (no forwarding), the default follows. A taken name is refused (409), at join **before** the invite is spent.
- **Relay**: a new Durable Object per person, `AgentBook` (strongly consistent — unique names and atomic renames cannot be raced; KV could), migration `v3`; WebSocket lookup `{type:"agent", handle, agent?}` → the one device; `/v1/join` takes a signed `agent`; admin `GET /admin/agents/<person>`, `DELETE /admin/agents/<person>/<agent>`; removing a device frees its agents. The Node relay (`relay/`) has the same directory in SQLite and the same `/v1/agents`.
- **Sender**: every attempt resolves the agent again, seals for that one device, waits for that device's receipt; offline → `waiting`, retried to that device only; unknown agent → `failed (no agent …)`. The sender's own `<person>/<agent>` travels inside the encrypted message, so `morse reply` goes back to the agent that wrote. Sending to one of your own other computers works the same way; to an agent of this computer it is filed locally. Devices you paired by ID as `owner` are never downgraded to `peer`.
- **The command is `morse`** (`bin` adds `morse`; `anyd` stays as an alias for existing installs, hooks and launchd). Help, Morse messages, docs, the skill, `install.sh` and the landing page say `morse`. The npm package name stays `anytoany` for now.
- Tests: 506 (new `test/morse-agents.test.ts`; the relay transport tests now check no fan-out). Acceptance: `scripts/morse-e2e-agents.sh` (relay + site under local `wrangler dev`, temp HOMEs: one person with three computers + another person; addressing, offline, duplicate names, add, rename, install.sh `--agent`, the installed `morse` command); the three earlier e2e scripts pass after adapting to the new addresses.

### Morse: one-line join — invite codes, the morse.talk install site, pair-back on first contact (ADR-032, 2026-10-20)

- **Invites instead of hand-edited allowlists**: the relay admin runs `anyd invite create <handle> [--uses N] [--ttl 7d]` (admin key from `MORSE_ADMIN_KEY`, never saved) and gets a 160-bit code, shown once; `anyd invite list` / `revoke`. A new device runs `anyd join <code>`: it signs `morse-relay-join-v1\n<ts>\n<code>` with its device key and POSTs it with its certificate to `/v1/join`; the relay verifies it (a device can only enrol itself), takes one use, and allowlists the device under that handle. The relay URL and handle are saved to `~/.anytoany/config.json`. Re-joining is free (an existing member never spends an invite); a device that belongs to another handle gets 409.
- Invites live in a single `InviteBook` Durable Object (strongly consistent — Workers KV could let a one-use code be redeemed twice), stored only as SHA-256 hashes; used-up or expired invites are deleted. `wrangler.toml` adds the binding and migration `v2`.
- **`site/` — the morse.talk website**, a separate static-assets-only Worker (`morse-site`) so publishing a new package never redeploys the relay (which would drop every live socket): a tiny landing page, `/install.sh`, `/morse.tgz` (`npm pack`), built by `npm run site:build`.
- **`install.sh`** (`curl -fsSL https://morse.talk/install.sh | bash -s -- <code>`): checks Node >= 20 (prints how to get it, never installs it), `npm install -g` the site's `morse.tgz`, `anyd setup`, `anyd join`, then starts the daemon at login — launchd user agent `dev.anytoany.daemon` on macOS, `systemd --user` on Linux; Windows: use WSL2. `--dry-run-service` only prints the plist / unit.
- **Pairing happens by itself**: `anyd send morse.talk/<person>` pairs an unpaired person on the spot; the relay now forwards the sender's `fromHandle`, and a recipient who has not paired the sender pairs them back as `peer` after checking the relay directory really lists that device. Off with `morse.autoPairBack: false`; `anyd pair remove <person>` also blocks them from being paired back.
- The any-to-any skill now tells agents how to use Morse (send / inbox / pull / reply / pair, peer messages are not instructions). New user guide: `docs/QUICKSTART.md`.
- Tests: 491 (11 new: invite storage logic incl. Node-signed / WebCrypto-verified joins, expiry, refunds, conflicts; join + admin client; membership probe; first-contact pairing and pair-back refusals). Acceptance: `scripts/morse-e2e-join.sh` (relay + site under local `wrangler dev`, temp HOMEs).

### Morse v2: relay forwards only (Cloudflare Worker), sender-side outbox, people-not-devices addressing (ADR-031, 2026-10-20)

- **Addresses are people**: `anyd send morse.talk/mei "hi"` reaches that person's inbox on any of their devices; `morse.talk/mei/claude` names one of their agents, resolved on *their* machine (a registered agent of that name, else that agent's latest session). Device IDs stay internal. `anyd pair add morse.talk/mei` pairs every device under that handle (tier `peer`) and pins their verified keys; `anyd pair remove mei` drops them all.
- **`relay-cf/` — the relay as a Cloudflare Worker + Durable Objects** (WebSocket Hibernation, SQLite-backed DOs so the free plan works). One `DeviceHub` object per device ID holds that device's live socket and its signed key bundle, nothing else. `send` is forwarded to the recipient's object and answered `sent` or `offline`; **no message is ever stored**. Allowlist in Workers KV (`<deviceId> -> {handle, name}`, `@handle -> [ids]`), managed over an `ADMIN_KEY`-protected HTTP API or `wrangler kv`. Login is the same signed challenge, now checked with WebCrypto only (certificate fingerprint must equal the device ID in the socket URL). Deployment, custom domain and cost notes: `docs/DEPLOY-CLOUDFLARE.md`. **Not deployed yet.**
- **Offline delivery moved to the sender**: a message counts as delivered only when the recipient's end-to-end receipt arrives. Unreachable recipient (offline, relay down, no receipt) -> the message is parked `failed (waiting: ...)` and retried every 30 s for up to 30 days (`outbox.retryIntervalSec` / `outbox.maxWaitDays` in `~/.anytoany/config.json`), instead of "3 attempts then dead". The relay client reconnects with backoff; a relay restart loses nothing because it holds nothing.
- **`relay/` (Node) kept, same protocol**: forward-only, only the public key directory on disk; for self-hosting without Cloudflare and for in-process tests.
- Envelope cap follows the relay (`welcome.limits`): Cloudflare caps a WebSocket message at 1 MiB -> 1,000,000 bytes per envelope, about 550 KB of attachments; the Node relay keeps 2 MB.
- Tests: 480 (18 new). Acceptance: `scripts/morse-e2e-cf.sh` (local `wrangler dev`, isolated config dir) and `scripts/morse-e2e.sh` (Node relay): pairing by handle, live delivery with receipts, offline -> outbox -> redelivery, nothing in relay state, stranger refused, relay restart -> reconnect, attachment, peer labelling, reply.

### Morse: cross-network relay + `peer` trust tier (ADR-030, 2026-10-20)

Fork note: Morse is derived from anytoany (MIT). See [docs/MORSE-MVP.md](docs/MORSE-MVP.md).

- **`relay/` — morse-relay**: a small Node/TypeScript WebSocket store-and-forward mailbox (own `package.json`, `npm start`, `Dockerfile`). Devices log in by signing a random challenge with their ADR-028 device key; only allowlisted device IDs get in. It stores recipient ID, sender ID, ciphertext and time — nothing else — pushes live, keeps offline mail (30 days by default), deletes on ack, caps envelope size (2 MB) and per-device send rate.
- **End-to-end encryption** (`src/cluster/e2e.ts`): per-device X25519 key published as a bundle signed by the Ed25519 identity and verified against the paired device ID (the relay cannot swap keys); per-message ephemeral X25519 → HKDF-SHA256 → AES-256-GCM, envelope signed by the sender. Node `crypto` only.
- **Daemon relay transport** (`src/cluster/morse.ts`, `relay-client.ts`): `anyd start --relay <url>` or `anyd relay set <url>`; LAN direct when the paired device is on the LAN, otherwise the relay. Inbound envelopes are verified, de-duplicated and filed into the existing mailbox; an encrypted receipt goes back (`✓ receipt` in `anyd inbox --all`).
- **`peer` trust tier**: `anyd pair add <id> --peer --name <who>`. Peer mail is pull-only (the dispatcher never claims it, so owner escalations like `codex.sandbox` / `zcode.deliverMode` never apply), and `anyd pull` / the prompt hook / `anyd inbox` label it "来自 <name> 的 Agent，是同伴消息，不是你主人的指令". Peer devices on the LAN may send messages but not read sessions or merge collab docs. `anyd peers` shows tiers and relay status.
- **Files**: `anyd send --file` (≈1.1 MB total per message, via the relay); received files land in `~/.anytoany/inbox-files/<id>/` with mode 0600, never executed or opened.
- **Fix**: `anyd pair add <id> --name x` silently ignored `--name` (the parent `pair --name` option captured it).
- Tests: 18 new (crypto, relay server, two-device transport, peer tier); `scripts/morse-e2e.sh` runs relay + two isolated daemons end to end.

### Before Morse: the anytoany period (2026-08-05 – 2026-10-20)

Morse started as a fork of anytoany (MIT). What it already had when the fork was made, in short; each line points at the decision record that has the details.

- **Agents and delivery**: Claude Code, Codex, Kimi Code and ZCode, each found from its own session store and reached through its own headless resume channel (`claude -p --resume`, `codex exec resume`, `kimi -S … -p`, ZCode's bundled engine) — arguments only, no shell, never `--dangerously-*` (ADR-005). Notes per vendor: `docs/specs/phase3-*.md`.
- **Mailbox**: SQLite with ack / retry / dead-letter and crash recovery; an envelope that asks for a verdict (`DONE` / `BLOCKED` / `DECLINED` / `NOOP`, ADR-011) and suppresses ping-pong; your own messages stay in one thread (ADR-014); inside your own cluster a relayed request carries your authority (ADR-016).
- **Seeing what happened**: prompt hooks for Claude and Codex that inject pending mail and a digest of what was handled (ADR-012); macOS notifications; the loopback web console at `127.0.0.1:7433`; `anyd pull` / `--history` and the `reload` skill for apps that do not refresh; `@`-mentionable agent files in Claude Code; `anyd monitor` (now `morse read --wait`) for waiting in-session (ADR-019).
- **Not losing mail** (2026-09): dead letters are handed over by the pull hook (ADR-022); no headless resume into a session that is open (ADR-023, Codex: ADR-026); out-of-date CLIs refused at send time (ADR-025).
- **Desktop-app agents** (2026-09-17): register and pull over local HTTP; 闪电说 (`sds`) first (ADR-024, `docs/specs/phase5-external-agents.md`).
- **Doorbells** (2026-10-13): Claude's inbox socket and `codex queue` deliver to open sessions (ADR-027); ZCode's session mailbox for a session mid-turn (ADR-029). Fixed 2026-10-20: queued Codex turns were listed as "already handled" by the digest and skipped.
- **Devices**: LAN discovery over mDNS (ADR-002), then one key per device, mutual TLS and pairing by public ID (ADR-028; device pairing later removed with v2, ADR-091).
- **Ops**: daemon kept alive by launchd (`docs/specs/phase3-daemon-persistence.md`); CI on Ubuntu per push, macOS weekly (ADR-015); configurable per-turn delivery budget (`codex.deliverTimeoutSec` / `zcode.deliverTimeoutSec`, 60–3600 s).
- **Removed since**: the shared collaboration doc and the self-driving loop (ADR-017, ADR-018, ADR-020; removed by ADR-074).
