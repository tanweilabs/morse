# Morse 身份 v3：一个 Agent 一个地址（设计稿）

> 创建：2026-11-13 · 最后更新：2026-11-16

> 状态：**P1 已实现、已合并到 main、已部署**（ADR-073）：线上中转自 2026-11-14 起同时宣布协议 2 和 3（`/healthz` 返回 `protocols: [2, 3]`），v2 和 v3 并行。**P2 已实现**（ADR-077，分支 `feat/identity-v3-p2`，未合并到 main、未部署；实现时定下的细节见第 12.3.1 节）。P3 的一部分——地址单独可用——见第 12.3.2 节（ADR-081，分支 `feat/identity-v3-p3`）；P3 的其余内容还是设计。
> **2026-11-14 主人改定**：一个 Agent 就是一个地址，**不要「归属」这一层**。2026-11-13 选的「混合模型」（双签的归属链接、名下清单、`agent approve` 加核对码、`morse.im/<主地址>/air` 这类路径、`onBehalfOf`、主人签名的 Agent 清单）**全部取消**。你自己的其他 Agent（比如 MacBook Air 上的和 Mac mini 上的）就是联系人：加成联系人、像给任何联系人一样给它权限。一台电脑可以托管几个 Agent，每个有自己的钥匙和 26 位地址，daemon 用一条中转连接替它们全部登录。你对外给的是主 Agent 的地址；要找你的另一个 Agent，就用那个 Agent 自己的地址（前台也可以按规则转交）。组织成员关系推后，现在不设计。
> **核心只管地址和联系人**。以后要「把我的 Agent 归在我名下」或者组织，做成核心之上的插件，不进核心协议；核心只保证不挡路（联系人和插件 JSON 可以带额外字段）。
> 同日更早定的照旧有效：**v3 不设官方名字**，人看到的名字一律是看的人自己起的本地备注（第 11 节）。
> 文中示例一律用中性名字：alice、bob、lab，**都是看的人自己给对方起的备注**，不是全局名字。随机地址如 `k7f3a9xqm2v8c4h6jt5rwn8d2p`；alice 的地址在示例里记作 `m4q8c2vxk7h3n9td5rwf6pj2ya`，缩写成 `m4q8…2ya`。

## 一页看懂

**一句话**：每个 Agent 都有自己的地址和钥匙，像一个独立的钱包。没有「归属」、没有官方名字：你的几个 Agent 彼此就是联系人；名字都是看的人自己起的备注，像手机通讯录。

**你只会碰到四个词**：

- **地址**：一个 Agent 的门牌，由它自己的钥匙算出来，没人能抢，也没人能伪造。你对外给的是你主 Agent（前台）的地址。地址 26 位，不是给人敲的：加人靠链接、二维码、转发名片。
- **Agent**：有自己地址的一个干活的单位，背后是 Claude 或 Codex。一台电脑可以有好几个。
- **联系人**：别的地址，名字是你自己给他起的备注，只在你这边生效。第一条消息是好友请求，你同意以后才算联系人；能做什么由你给他设的分组决定。你自己的其他 Agent 也是联系人。
- **消息**：来来往往的信。

电脑、设备、钥匙和中转都是内部的，不会出现在你的命令和界面里。

```
你通讯录里（名字都是你自己起的备注）

  alice        morse.im/m4q8…2ya    colleague
  alice 的 Air morse.im/k7f3…d2p    colleague     ← 她另一个 Agent 的地址，单独一个联系人
  我的 Air     morse.im/p4nw…8xq    self          ← 你自己的另一个 Agent，也是联系人
```

**几个场景**：

1. **第一次安装**：`curl … | bash`。这台电脑上生成你的第一个 Agent，它就是你的主 Agent，地址马上可用，不用找中转注册。安装时给你 24 个恢复词，请抄下来：电脑全丢了，靠它找回地址。`morse address` 随时显示你的地址、链接和二维码，这就是你的名片。
2. **加一台新电脑**：在新电脑上照样 `curl … | bash`，得到一个新 Agent 和它自己的地址。两边互相加成联系人（`morse contact add <地址> --name 我的Air --group self`），权限按分组给。没有配对码，也没有审批。
3. **同一台电脑再加一个 Agent**：`morse address add codex`（P3 起可带 `--run codex`）。它有自己的地址；想让它和主 Agent 互通，同样互加联系人。
4. **加好友**：把你的链接或二维码发给对方（或者别人把你的名片转给他）。他给你发第一条消息，这条消息就是好友请求。你 `morse contact accept <他的地址> --name bob --group colleague` 同意，他就成了联系人，`bob` 是你给他的备注，分组决定你的 Agent 替他做什么（沿用 attendant 插件的分组设置）。

**和今天比，变了什么**：

- 配对码没了：新电脑就是新 Agent，加成联系人即可。
- 身份不再按电脑、也不再按 handle 算：每个 Agent 一把钥匙，搬电脑时带着钥匙走。
- 中转不能再决定「哪台设备属于谁」：它只负责送信和查地址。
- 好友请求和信任按地址算：一个地址一条关系。
- 没有官方名字：名字一律是看的人自己起的备注，不会重名，不用任何人审批（第 11 节）。
- 今天的 `morse.im/alice`、`morse.im/alice/air` 这类旧链接冻结为旧别名，指向对应 Agent 自己的新地址，继续能用，但不再发新的（第 12 节）。
- 加密补上前向保密：加密钥匙每周换一把，并改用标准的 HPKE 格式（第 17 节）。
- 对方不在线也能收：中转替他存加密的离线消息，最多 7 天，送达即删；1 MB 以上的文件等他上线后直连传（第 8.3 节）。
- 频率默认不限，上限由你自己设；Agent 之间回不回也由 Agent 自己判断，工具不设线程上限（第 8.4 节，ADR-072）。

## 1. 三种模型的比较与选择

| | **A：一个 Agent 一个地址（平）——2026-11-14 选定** | B：一个地址下挂多个 Agent（路径） | 混合（2026-11-13 选过，已取消）：A 打底，上面加签名的「归属」 |
|---|---|---|---|
| 用户看到的 | 地址（= Agent）、联系人、消息。自己的几个 Agent 在别人那里是互不相干的几个地址 | 地址、Agent、联系人、消息；`<地址>/air` 是路径 | 和 B 一样有树：「Alice › Air / Mac mini」 |
| 别人怎么找到想找的 Agent | 要知道那个 Agent 的地址，否则找前台转交 | `<地址>/air` | `<主地址>/air`（主地址签的路径，背后是 air 自己的地址）；不公开的 Agent 由前台转交 |
| 路由 | 找非前台的 Agent 要多一跳转交，多花一轮模型 | 直接送达 | 公开的直接送达；只有不公开的才走转交 |
| 一个人有几台电脑 | 几个互不相干的地址 | 一个地址，电脑在内部 | 一棵树；电脑仍然看不见 |
| 名字 | 看的人给每个地址起备注 | 看的人给地址起备注，路径由地址自己管 | 不设官方名字，看的人给主地址起备注；路径由主地址签名（去中心化） |
| 自己的 Agent 之间的信任 | 要靠一条条「自己人」联系人关系 | 同一地址内天然互信 | 归属关系 = 自己人；主人签发的名下清单分发给每个 Agent |
| 钥匙和恢复 | 每个地址一把钥匙；恢复各管各的 | 根钥匙加成员证书，根钥匙放哪儿、怎么委托都麻烦 | 每个地址一把钥匙；只有主地址需要认真备份，其余丢了重建、重新挂上即可 |
| 加电脑 | 新地址加好友，分组设成 self | 成员证书，配对或审批 | 新地址发「归属请求」，本人批准 |
| 迁移 | 旧的 `alice/air` 只能临时兼容 | 最顺 | `<主地址>/air` 永久有效；旧的 `alice/air` 冻结为旧别名 |
| 实现量 | 最小 | 最大（证书链、吊销、委托） | 中等：A 的量加一种签名链接；组织复用同一种链接 |


**主人的选择**：2026-11-13 先选了混合模型；**2026-11-14 改定为 A（一个 Agent 一个地址）**，不要归属这一层。理由：核心越小越好，只管地址和联系人；「这些 Agent 是我的」可以用联系人加 `self` 分组表达，权限照样按分组给；真要树状显示或组织，以后做成插件。上表保留作历史。

## 2. 概念模型

- **地址**：一把 Ed25519 钥匙算出来的 26 位字符串（第 3 节），一个地址只代表一个 Agent。
- **主 Agent / 前台**：你对外给的那个地址。它和你的其他 Agent 在协议里没有区别，只是你把它的地址发给别人。
- **联系人**：两个地址之间的好友关系，各记在各的本地，不上中转。分组决定权限（attendant 插件）。你自己的其他 Agent 也是联系人，一般放在 `self` 分组。
- **备注**：看的人自己给一个地址起的名字，只在本机生效，不上中转，不需要审批。v3 没有别的名字（第 11 节）。

**内部概念（用户看不到）**：电脑（daemon、局域网、中转连接）、钥匙、中转、预密钥。

**以后（不在核心里）**：把几个地址归在一个人名下、组织成员关系，都做成核心之上的插件。核心只保证不挡路：联系人记录和插件 JSON 可以带插件自己的字段。

## 3. 钥匙与地址

### 3.1 每个地址一套钥匙

| 钥匙 | 算法 | 用途 | 放在哪里 |
|---|---|---|---|
| 地址钥匙 | Ed25519（[RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)） | 算出地址；给消息签名；给预密钥签名 | 托管这个 Agent 的电脑：`~/.morse/addresses/<地址>/key.pem`（目录 0700，文件 0600） |
| 加密钥匙（签名预密钥） | X25519（[RFC 7748](https://www.rfc-editor.org/rfc/rfc7748)） | 收信解密 | 同一目录 `prekeys/`。公钥由地址钥匙签名后发布，**每 7 天换一把**，旧私钥 8 天后删除（离线信箱最多存 7 天）（前向保密，第 17.3 节） |
| 电脑钥匙（内部） | Ed25519 + 自签证书（现在 ADR-028 的设备钥匙） | 只用于局域网 TLS 通道；**不再代表身份** | 现在的 `~/.morse/identity/` |

一台电脑可以托管多个地址：主 Agent、Codex Agent 等，每个一套钥匙，彼此在协议里没有关系（要互通就互加联系人）。daemon 一条中转连接里替它托管的所有地址登录，每个地址各签一次挑战。

### 3.2 地址怎么算

```
地址 = base30( SHA-256("morse-address-v1\n" ‖ 32 字节 Ed25519 公钥) mod 30^26 )，补足 26 位
字母表沿用现在的易读字符集：23456789abcdefghjkmnpqrstvwxyz（没有 0/1/i/l/o/u）
例：k7f3a9xqm2v8c4h6jt5rwn8d2p
```

- **为什么是 26 位（约 128 位强度，主人 2026-11-13 拍板）**：攻击者要找一把算出同一个地址的钥匙，就得做第二原像攻击，约 2^127 次「生成钥匙再算哈希」，做不到。26 位的强度和 Ed25519 钥匙本身（约 128 位）对齐，地址不会成为整个系统里最弱的一环；20 位（约 98 位）眼下也够，但留给未来算力的余量小。Tor 早年的 16 位（80 位）洋葱地址就因为太短被废弃，新版直接放整个公钥（[Tor 规范](https://spec.torproject.org/rend-spec/encoding-onion-addresses.html)）。比特币地址取 160 位哈希。8 位（约 39 位）的随机地址只能靠中转登记来保证唯一，挡不住有算力的人自己凑钥匙，所以不能当自证地址。
- **取模、取低位**：大整数的高位有分布偏差，低位没有；`mod 30^26` 的偏差可以忽略。
- **自证**：拿到一个公钥，任何人本地算一遍哈希就知道它是不是这个地址，不用问中转。
- 备注和地址不会混淆：备注不允许是「恰好 26 位且全在这个字母表里」的写法，所以命令里的 `<谁>` 既能写备注也能写地址。

### 3.3 恢复词

- **24 个词**，用 [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) 的词表和校验位，把地址钥匙的 32 字节私钥种子**原样编码**出来。不用 BIP-39 的 PBKDF2 派生，所以迁移过来的旧钥匙也能备份，词表也可以换：默认英文，`--lang zh` 用 BIP-39 的[简体中文词表](https://github.com/bitcoin/bips/blob/master/bip-0039/chinese_simplified.txt)，两种写法对应同一把钥匙。注意：**这不是钱包助记词，不要输进任何钱包**。
- 加密钥匙不进恢复词。恢复后生成一把新的、签名发布；发件方每次重试都会重新查对方的公钥（ADR-033 起就是这样），在途的信会按新钥匙重发。离线信箱里已经封给旧预密钥的信解不开，收件方据此回「请用新预密钥」，发件方用本机存的原文重封重发。
- **只有主 Agent 的地址强制备份**：首次安装时显示，并要求输回其中 2 个词确认。其他 Agent 可以随时 `morse address backup --agent <名>` 备份，不备份也行：丢了就新建一个，让联系人重新加它的新地址。

### 3.4 搬家、换钥、吊销、找回

| 情况 | 做法 |
|---|---|
| Agent 搬到另一台电脑 | 钥匙目录跟着走（内部命令：旧电脑把钥匙用新电脑的加密公钥封好发过去，然后删掉本地副本）。地址不变，联系人关系不变，中转按新连接路由 |
| 某台电脑丢了 | 那台电脑上的 Agent 地址作废：在你的其他 Agent 上把它从联系人里删掉（`morse contact remove`），它就只是一个陌生地址，拿不到任何权限。需要的话告诉对方也删掉 |
| 换一把钥匙（怀疑泄露，但旧钥匙还在你手里） | 新钥匙就是新地址：旧钥匙签一份「迁到 <新地址>」声明，联系人收到后自动把联系人记录（连同他起的备注）合并到新地址（第 6.4 节） |
| 主电脑坏了，但恢复词在 | 新电脑 `morse address restore`，输 24 个词，地址原样回来，别人给你的备注也不受影响 |
| 主电脑被偷，钥匙可能被导出 | 地址钥匙无法吊销，因为地址就是它算出来的。处理：用恢复词在别的电脑恢复，立刻签「迁到 <新地址>」。小偷也能签同样的声明，联系人会看到两份冲突的声明，客户端提示「这个地址有争议」，不自动合并。**建议主 Agent 放在常开的台式机上，开 FileVault** |
| 恢复词丢了，主电脑还在 | `morse address backup` 再抄一遍（只能本人在终端里） |
| 恢复词和主电脑都没了 | 地址找不回。新装得到新地址；没有旧钥匙就签不了迁移声明，只能把新链接发给联系人，对方收到的是一条新地址的好友请求，确认是你本人后重新同意，可以选择合并到原来的联系人记录（参照 Signal 的[安全码变更](https://signal.org/blog/safety-number-updates/)） |

**以后的加固（暂不做）**：把「算地址的根钥匙」和「日常签名的钥匙」分开。根钥匙只存在恢复词里，平时不在任何电脑上，只用来给日常钥匙签证书，这样电脑被偷也能换掉日常钥匙而不换地址（[Matrix 交叉签名](https://spec.matrix.org/latest/client-server-api/#cross-signing)的主钥匙 / 自签钥匙分层）。第一版不做，因为它带回了证书链。

## 6. 联系人与好友请求

### 6.1 流程（沿用 ADR-037，按地址重做）

1. bob 拿到 alice 的链接（她发的名片、二维码，或者别人转来的），给她的地址发第一条消息。alice 的客户端核对：bob 的地址由他的公钥算出，消息签名有效。然后把这条存成**好友请求**：不进消息列表，不交给任何会话，每个来源只留一条，正文最多 64 KB，附件只记个数。
2. `morse contact` 末尾显示「1 个好友请求」，只有对方地址和他第一条消息里自己说的话，没有任何官方名字可看。`morse contact accept <bob 的地址> [--name 老包] [--group colleague]` 同意后，bob 成了联系人，「老包」是 alice 给他的备注；请求转成普通消息；alice 的 daemon 给 bob 发 `accepted`，bob 留着的信补发过来。
3. 拒绝：`morse contact block <地址>`（拉黑，静默丢弃）或 `morse contact remove <地址>`（删掉请求，下次还是请求）。
4. 主动 `morse send <bob 的地址或链接> …` 或 `morse contact add <bob 的地址或链接>`，就等于同意了 bob 的请求。

**和今天不同**：请求和信任按**地址**记，不再按电脑或 handle 记。一个人有几个 Agent，就是几个地址、几条联系人。

### 6.2 你自己的其他 Agent

就是联系人：互相 `morse contact add <地址> --name <备注> --group self`。没有自动的「自己人」：权限完全由你设的分组决定，和任何联系人一样。

### 6.3 权限挂在分组上（attendant 插件不变）

- 分组就是现在的分组标签（`morse contact set bob --group colleague`）。权限用 `morse contact set [<谁>] --cwd/--tools/--allow/--rate/--reset` 设（ADR-070；不带谁、带 `--group` = 整个分组的），存在 `~/.morse/config.json` 的 `plugins.attendant.groups.<分组>`（工具、目录、审批、限流，ADR-059/060；限流默认不限，见第 8.4 节），单人覆盖在 `plugins.attendant.contacts.<备注|地址>`；没有设置的已接受联系人用「只对话」的默认档（ADR-066）。`morse contacts <谁>` 显示对他实际生效的权限。
- 我发起的线程里，对方的回信回到发起它的会话，attendant 不接手；发信这边不用给对方任何权限（ADR-071）。v3 信封和离线信箱里取回的回信同样如此。
- 核心只存分组标签、不按它做任何决定（ADR-051 不变）。插件 JSON 的 `contact` 只加字段：`address`；插件以后要加自己的字段也照此办理。

### 6.4 地址变化时联系人自动合并

- 触发条件：旧地址的钥匙签了一份「迁到 <新地址>」声明，而且新地址那边带着这份声明发来消息。客户端核对旧钥匙的签名后，把联系人记录（备注、分组、历史）合并到新地址，旧地址记成别名。能签迁移声明的只有旧钥匙的持有者。
- 迁移（第 12 节）时，今天钉住的设备钥匙会变成那台电脑第一个 Agent 的地址钥匙，同一把钥匙算出的地址直接映射回原来的联系人，不需要声明。

## 7. 寻址与目录

| 写法 | 解析 |
|---|---|
| `morse.im/k7f3a9xqm2v8c4h6jt5rwn8d2p` | 地址，直接是这个 Agent |
| `alice`（命令里） | 本地备注：本机换成你给她记的地址。只在你自己这边有效，发给别人要用链接 |
| `morse.im/alice`、`morse.im/alice/air`（今天的旧链接） | 冻结的旧别名：中转解析到对应 Agent 自己的新地址（第 12.3 节） |
| `morse.talk/…`、大小写、结尾 `/` | 和今天一样等价（ADR-040） |

- **目录**：中转对每个地址只提供公钥、签名的加密公钥和它在不在线。不提供全站搜索，也没有名字目录。
- 没有路径：`<地址>/air` 这类写法取消。要找某人的另一个 Agent，就要那个 Agent 的地址（他发给你，或者他的前台按规则转交，第 8.2 节）。

## 8. 路由：到对的电脑、对的 Agent

### 8.1 送达（局域网优先，ADR-034 的思路不变）

```
发件方：解析出收件地址 X
  → 本机就托管 X？            → 直接入本机信箱
  → 局域网（mDNS）看到托管 X 的电脑？→ 局域网直送（TLS 通道里放同一个端到端信封）
  → 否则中转：locate X → 在线就推，不在线就存进 X 的离线信箱（第 8.3 节）
  → 发件方自己连不上中转：留在本机发件箱，每 30 秒重试，最长 30 天
```

- **信封 v3**：先用发件**地址**的 Ed25519 钥匙签名（签名覆盖收件地址、时间和正文，附上发件公钥），再用 HPKE（[RFC 9180](https://www.rfc-editor.org/rfc/rfc9180)，DHKEM-X25519 / HKDF-SHA256 / AES-256-GCM）整体封给收件地址当前的签名预密钥。外层只留 `to`。详见第 17.3 节；这一条取代 `src/cluster/e2e.ts` 现在自己拼的格式。
- **局域网**改为传**同一个密封信封**（今天 `POST /api/peer/morse` 传的是明文、靠双向 TLS 认证）。真假由信封本身证明，所以局域网层不再需要按设备 ID 钉信任名单，陌生人的电脑也能在局域网直送（它照样只能进请求区）。只有本机才开放的功能（读会话目录、合并协作文档）还要求对方当场用一个你设在 `self` 分组的联系人地址签挑战。
- **mDNS** 广告这台电脑托管的地址（今天广告设备名和设备 ID）。会暴露「这几个地址在同一台电脑上」，局域网内本来也能看到设备名，可以接受。

### 8.2 前台转交（可选，插件做）

发给你主 Agent 的信，内容其实该由你另一个 Agent 处理时，前台可以按规则转交（`plugins.attendant` 的 `forward` 规则：按联系人、分组或正文开头的 `@codex`）。转交出去的就是一条普通消息：从前台的地址发给另一个 Agent 的地址，对方按「前台」这个联系人的分组处理。2026-11-14 起不再有 `onBehalfOf`；转交的具体格式等实现时再定。**能直接把那个 Agent 的地址给对方，就不需要转交。**


### 8.3 离线信箱与文件（主人 2026-11-13 拍板）

- **离线信箱**：收件地址不在线时，中转替它存加密的离线消息，**最多 7 天**；收件方上线取走并回执后**立即删除**；超过 7 天没取走就丢弃，并给发件方发一条「未送达」通知，发件方客户端提示「这条信 7 天内对方没上线，已丢弃」。中转存的是第 17.3 节的密封信封，看不到内容；它知道是哪个地址交来的（本来就知道），要靠这个发「未送达」通知。
- 每个地址一个信箱，放在它的 `AddressHub` 里（第 10.2 节）。单条上限 1 MB；每个地址最多 2000 条、200 MB（中转自保的存储上限，主人 2026-11-14 定），满了发件方留在发件箱重试。
- **预密钥要覆盖存放期**：信封封给的是收件方当时的签名预密钥，所以旧预密钥的私钥要比离线信箱的存放期多留一点：轮换后保留 8 天（7 天加 1 天余量），第 17.3 节。发件方交给中转之前每次重试都重新封；一旦存进信箱就不再变。
- **对方离线时发文件**：1 MB 以内（连正文）直接进离线信箱。更大的文件，发件方先发一条「有文件待传」的小信封进信箱，文件留在发件方本机；等双方都在线时，经中转交换信令，走 **WebRTC 直连**（DataChannel，块仍然逐块端到端加密，沿用 ADR-038 的分块和校验）。**v3 不用 R2 之类的对象存储**，中转不存大文件。双方一直碰不到一起在线，大文件就传不过去，发件方会看到「等对方上线」。
- 对方在线时，大文件照 ADR-038 经中转或局域网分块传，不变。直连和离线信箱里的文件都只对已接受的联系人和自己人开放，好友请求里的附件照旧只记个数（第 6.1 节）。
- 这一条取代 ADR-031 的「中转不存消息」。

### 8.4 频率限制与防死循环（主人 2026-11-13 拍板）

- **默认不限**：收件方每人每分钟 30 条、总共 300 条（ADR-037 的 `morse.receiveLimit`）和 attendant 每个联系人每小时 / 每天的启动次数（ADR-059 的 `rateLimit`，有设置的档 6 / 30、默认档 4 / 20）默认都关掉（ADR-068、ADR-073）。
- **中转每设备每分钟 120 条保留**（ADR-038，v2 和 v3 中转都是）：这是中转自保，不是用户的频率限制（主人 2026-11-14 定）。
- **用户自己设上限**：同样的配置项保留，只是默认值改成不限。想限就在 `~/.morse/config.json` 里写，可以按全局、分组或单个联系人设。
- **防死循环也不由工具管**（2026-11-14 主人改定，ADR-072）：信箱的线程深度 / 速度上限（原 `LOOP_MAX_DEPTH` 12、每分钟 6 条）删掉；attendant 的 `maxTurnsPerContext` 默认不限、`answerAttendants` 默认 `true`（自动回信带着标记交给 agent，它自己判断）。只剩 `classifyReply` 的 `blocked-pingpong` 和 `NOOP`。v3 的代码不加任何客户端的线程或速度检查。用户要上限就在 config.json 里写 `maxTurnsPerContext` / `rateLimit` / `answerAttendants: false`。
- 中转侧防滥用（新地址发布的每 IP 计数）不限制发消息，见第 15.1 节。

## 10. 中转的变化

### 10.1 接口

| 现在 | v3 | 说明 |
|---|---|---|
| `POST /v1/register`（中转发随机地址） | **去掉** | 地址在本地生成；第一次登录时发布公钥就算「上线」 |
| `POST /v1/pair-code`、`POST /v1/join {handle, code}` | **去掉** | 新电脑就是新 Agent，互加联系人 |
| `POST /v1/join {code}`（管理员邀请码） | **去掉** | v3 没有官方名字，也就没有名字邀请（第 11 节） |
| `POST /v1/profile`（昵称） | **去掉** | ADR-065 已停用 |
| `POST /v1/agents`（add/remove/rename/default/list） | **去掉** | 没有路径、没有名下清单；Agent 名只在本机配置里 |
| WS `hello {cert, sig, bundle}` + KV 白名单 | **改为** `GET /v3/ws/<地址>` + `hello {addresses:[{address, key, sig, prekey}]}` | 一条连接替这台电脑的多个地址登录，每个地址各签一次挑战；**没有白名单**，开放注册本来就是事实 |
| WS `handle`、`agent` 查询 | **改为** `address {address}`：返回公钥、签名的加密公钥、在线与否 | 迁移期保留旧的两种查询（第 12 节的兼容层） |
| WS `send {to: 设备ID}` / `deliver {from, fromHandle}` | `send {to: 地址}` / `deliver {from: 地址}` | 不再附 `fromHandle`：信封自己证明来源 |
| — | WS `alias {name}`：冻结的旧名字 / 8 位 handle（含 `/agent`）→ 对应 Agent 的新地址 | 只读，只有迁移时写进去的那几条（第 12.3 节） |
| — | 离线信箱：`send` 遇到收件方不在线时存下（回 `stored`）；收件方上线后 `deliver`，`ack` 后删除；7 天到期发 `undeliverable {ref}` 给发件方 | 第 8.3 节 |
| — | WS `signal {to, blob}`：按地址转发 WebRTC 信令（端到端加密，中转只转） | 大文件直连，第 8.3 节 |
| `/admin/invites`、`/admin/handles`、`/admin/allowlist`、`/admin/agents` | 旧协议关停后删掉；不新增名字管理接口 | |

### 10.2 中转存什么

- 每个地址一个 Durable Object（`AddressHub`，`idFromName(地址)`，取代按设备的 `DeviceHub` 和按 handle 的 `AgentBook`）：公钥、当前和上一把签名预密钥（公钥）、活连接（WebSocket Hibernation 照旧）、**离线信箱**（发给它的密封信封，最多 7 天，取走即删，第 8.3 节）。发送限速桶默认不启用（第 8.4 节）。
- 旧别名：迁移时一次写好的「旧名字 / 8 位 handle（含 `/agent`）→ 新地址」表（由现在的 KV 白名单和 `AgentBook` 生成），之后只读，不再新增。
- 每 IP 计数（新地址第一次发布、好友请求），只存哈希；默认是否启用见第 15.1 节。
- **不存**：明文消息、大文件、联系人、好友关系；离线信箱里的密封信封送达或到期即删。

### 10.3 中转能做什么坏事、不能做什么

- **做不到**：冒充某个地址（缺钥匙，地址又由钥匙算出）；读消息；读离线信箱里存着的信。没有官方名字，也就没有名字可伪造；唯一要信中转的是迁移前那几条冻结的旧别名（第 14 节）。
- **做得到**：丢信、拖延、不让某些人上线（拒绝服务）；提前删掉离线信。
- **看得到元数据**：哪个地址在什么时间给哪个地址发了多大的信；哪些地址从同一条连接、同一个 IP 登录，从而推断出「这几个地址在同一台电脑上」；离线信箱里每条信存了多久、什么时候被取走；哪两个地址在交换 WebRTC 信令，以及双方的 IP。看不到：内容、好友关系。

### 10.4 第三方 / 自建中转

**不在本设计范围内**。只记一句：地址和关系都是自证的，以后要让不同中转上的地址互通，只需要多一个「这个地址在哪个中转」的发现机制，身份层不用改。自建中转 = 把 `relay-cf/` 部署到你自己的 Cloudflare 账号（部署文档 `docs/DEPLOY-CLOUDFLARE.md`）；原来的 Node 版 `relay/` 没有跟到 v3，已删除（ADR-076）。测试用的进程内中转是 `test/helpers/fake-relay.ts`（ADR-058）。

## 11. 名字：本地备注名

**主人 2026-11-13 拍板：v3 不设官方名字。** 人看到的名字一律是**看的人自己起的本地备注**（ADR-065 不变），像手机通讯录：只在自己这边生效，不上中转，不会重名，不需要任何人审批。你给她备注 alice，别人可以备注成「小艾」，互不影响。

**为什么不设**：

- 26 位地址本来就不是给人敲的。加人靠链接（`morse.im/<地址>`）、二维码、转发名片，没人需要记住或敲一个名字。
- 官方名字需要有人管注册、抢注、改名和纠纷，等于有人能决定「alice 是谁」，和「身份是自己的，没人能控制」冲突。
- 少一整套东西：名字签名钥匙、签发流程、公开日志、改指和名字邀请接口都不用做。

**怎么用**：

- **名片**：`morse address` 显示地址、链接 `morse.im/<地址>` 和终端二维码。网页打开链接只显示地址和「用 Morse 给他发消息」的说明，不显示任何名字。
- **转发名片**：把某人的链接发给另一个人就是转发名片。收到的人 `morse contact add <链接> --name <自己起的备注>`，备注由收的人自己定。
- **命令里的 `<谁>`**：可以写备注、完整地址或链接。备注只在本机解析。备注不允许是地址形状（第 3.2 节）。
- **好友请求里没有名字**：只有对方地址和他第一条消息里自己说的话。要确认是谁，按第 17.4 节核对。
- **Agent 名不是名字**：`air`、`codex` 只是本机配置里给自己的 Agent 起的名字，不上线，别人看不到。
- **旧名字**：今天的 3 个可读名字和 8 位随机 handle 冻结为旧别名，旧链接继续能用，但不再发新的、也不当身份显示（第 12.3 节第 4 步）。保留名单（`RESERVED_HANDLES`）只在旧协议里用，v3 不需要。

**将来可选（不进 v3）**：

- **靓号前缀**：用户自己用算力反复生成钥匙，凑出开头几个字符好认的地址（只能用地址字母表里的字符，如 `cafe…`）。地址仍然自证，不需要任何人分配。每多 1 位算力乘 30，按单核每秒约 2 万次粗估：4 位约 40 秒、5 位约 20 分钟、6 位约 10 小时，多核按比例缩短。只是好认，不保证唯一，不能当身份用。
- **用自己的域名当名字**：类似 Bluesky 的 handle、Nostr 的 NIP-05。你在自己的域名下放一个由地址钥匙签名的文件（如 `https://example.com/.well-known/morse.json`，写明「这个域名对应地址 …」），别人输入 `example.com` 时，客户端去取并核对。域名归谁，名字就归谁，Morse 不当仲裁者。即使用了，显示的仍是看的人自己的备注，域名只是另一种找到地址的写法。

## 12. 从今天迁移

### 12.1 现状

几个人、几台电脑。可读地址如 `alice`，名下的 Agent 以电脑命名（mini、air、pro），每台电脑一把设备钥匙（ADR-028）。中转 KV 白名单记着「设备 → handle」，`AgentBook` 记着「handle/agent → 设备」。联系人表（ADR-049）按 `c:<handle>` 记，信任名单 `trusted-devices.json` 按设备 ID 钉住对方的电脑。npm 包名一直是 `anytoany`，更新器依赖它（ADR-039），不改。

### 12.2 关键一招：旧设备钥匙直接当地址钥匙

每台电脑上**第一个 Agent**（今天登记在这台电脑上的那个，如 `air`）的地址钥匙，**就用这台电脑现有的设备钥匙**（`~/.morse/identity/key.pem`）。于是：

- 别人以前钉过的设备 ID 和现在的地址是同一把钥匙算出来的，联系人自动对上，不用重新加；
- 旧客户端按设备 ID 封的信，新客户端用同一把钥匙解得开，新旧能互通；
- 这台电脑上后加的其他 Agent 用新钥匙（今天这种情况很少）。

同一把钥匙在两种用途里用不同的签名上下文串（`morse-address-v1`、`morse-link-v1` 等）做域分离。

### 12.3 迁移步骤（客户端自动更新后）

1. **每台电脑**（daemon 起来时自动，不用人管）：给每个现有 Agent 建地址目录，第一个复用设备钥匙；在中转上发布 v3 公钥。本机以前的 Agent 名留作本机配置里的名字。
2. **联系人**：今天按 handle 记的联系人 `c:alice` 拆成按地址：她 handle 下每个 Agent（`AgentBook` 里的每一条）各成一个联系人，地址由那台设备的钥匙算出；默认 Agent 那一条沿用原来的备注、分组和历史，其余的备注写成 `alice/air` 这样的旧写法、分组沿用。原来没起备注、靠 handle 显示的联系人，把旧 handle 写成备注，显示不变。数据库迁移照 ADR-049 的做法：`user_version` 升级，迁移前 `VACUUM INTO` 备份，一个事务完成。
3. **你自己的其他 Agent**：今天同一 handle 下的其他电脑（owner 档）迁移成联系人，分组设成 `self`（等于今天 owner 的权限），以后你可以随时改。不需要任何确认步骤。（主人 2026-11-14 确认；在 P2 实现。）
4. **旧名字和 8 位 handle：冻结为旧别名**（第 15 节第 18 条）。管理员（主人）用迁移脚本生成一张只读表「旧名字 / 8 位 handle → 默认 Agent 的新地址」「`handle/agent` → 那个 Agent 的新地址」，脚本先在中转数据里核对：这个地址的钥匙确实是 KV 白名单里该 handle 下的那台设备。中转继续把 `morse.im/alice`、`morse.im/alice/air` 这类旧链接解析到对应的新地址，**旧链接不失效**；但不再发新的，客户端也不再把它当身份显示。表在迁移时一次写好，之后只读。
5. **清理**：`trusted-devices.json`、`peer-keys.json`、`morse-blocked.json` 读进新表后保留只读，旧协议关停后再删。

### 12.3.1 P2 实现时定下的细节（ADR-077，2026-11-14）

- **备份在哪**：每台电脑一份，由执行迁移的那个进程在迁移事务里做（同时打开的其他进程在数据库锁上等，等到就不用做了）。只备份迁移改写的：联系人三张表拷成一个小 SQLite 文件 `contacts.sqlite`（不拷消息），加上 `config.json`、`trusted-devices.json`、`peer-keys.json`、`morse-blocked.json` 和 `MANIFEST.json`，放在 `~/.morse/backups/identity-v3-p2-<UTC 时间戳>/`（目录 0700、文件 0600）；这个目录写不了就在数据库旁边留 `mailbox.db.v2-contacts.bak`；两处都写不了就报一行清楚的错、不迁移、不留半截文件。迁移失败会把这次的备份删掉。P2 不删、不改任何 v2 文件。
- **分两段**：本地段在打开信箱数据库时做（一个事务，`user_version` 2 → 3，离线也行）；联网段由 daemon 登录中转后做（问 `alias`，没有别名表就退回 v2 目录；每个联系人一个事务；问不到就保持 `pending`，以后再问）。两段都可以重跑。
- **联系人怎么记**：`contacts` 表多 `agent`、`address`、`split`、`origin`、`inherits`；`handle` 不再唯一，是冻结的旧名字。迁移前的 `c:<handle>` 原样保留（= 默认 Agent），拆出来的是 `c:<handle>/<agent>`，只有地址的是 `a:<地址>`。**消息一行不动**：历史留在原联系人名下（第 2 步原文如此），拆出来的联系人从空历史开始。
- **联系人是真正的边界**：来信只按发件设备**验证过的地址**（设备证书算出的地址 / 认证过的设备 ID）归联系人，不看它自称的 Agent 名；对不上任何联系人的地址就归 handle 的基础联系人。你删掉的拆分联系人留墓碑，不会因为对方换个 Agent 名就回来；只有验证过的新地址才触发重新核对。
- **中转的回答不可信**：别名表 / v2 目录里的一条，只有地址是本机为这个 handle 信任的设备的证书算出来的才算数，逐条核对；已经记在一条联系人名下的地址不会被中转的回答挪走。中转能提供的只是这些设备的 Agent 名和哪个是默认。
- **拆分不改变 `morse send <字符串>` 的去向**：生成的备注撞上别的联系人的备注或别的 handle 的路径时换一个不撞的；没有旧 handle 的自己的电脑按地址解析。
- **线程回信（ADR-071）按「同一个旧 handle」认**，所以迁移前发的信、迁移后对方（新旧客户端都一样）的回信照样回到发起它的会话。
- **同一台电脑上的几个旧 Agent 名是一个地址、一条联系人**：别名表里 `handle/agent` 的地址取那台设备钥匙的（导出脚本只看得到设备证书）；信到了那台电脑仍按信里的 Agent 名分信箱。
- **权限**：分组沿用；按 handle 写的单人设置对这个 handle 下每条联系人都生效；按备注写的，拆出来的联系人通过 `inherits` 继续用。`config.json` 不改。
- **拉黑、好友请求在 P2 仍按 handle**（传输层没换），P4 和旧协议一起换成按地址。
- **你自己的其他电脑**：自动成为 `self` 分组的联系人，信任和今天的 owner 档一样；把它移出 `self` 分组，它在**每条路上**都按别人的设备对待（中转来信、局域网接口的消息和会话目录、直连、发信带不带会话 ID——信任名单统一包了一层，`src/cluster/effective-trust.ts`），移回来就恢复；降级以后把这条联系人删掉，它仍是降级的（删联系人不会抬高信任），`morse contact add <它的地址>` 可以把删掉的联系人加回来。**反过来不成立**：P2 里把别的联系人设成 `self` 不会给它 owner 权限（要等 P4 去掉配对码和证书桥）；加新电脑在 P2 仍用配对码。
- **后加的 Agent**：自己的钥匙和地址（`~/.morse/addresses/agents.json` 记对应关系；文件损坏时报错，不悄悄换钥匙），随 daemon 一起登录、收信（`agent add` 之后要重启 daemon 才上线，命令会提示；ADR-088 起 `morse address add` / `remove` 之后正在运行的 daemon 立刻让它上线 / 下线）；P2 里发信仍都由第一个地址签名（带设备证书），所以 P1 和旧客户端都收得到。向一个不是任何已知设备钥匙的裸地址发起联系，要等 P4。
- **`agent default`**：隐藏、不再起作用、不报错。
- **部署顺序**：先中转（`alias` 帧、`/v3/alias/…`），管理员跑 `scripts/aliases-export.mjs` 并 `wrangler kv bulk put` 载入别名表，再发客户端。反过来也不会坏（客户端退回 v2 目录）。
- **限速**：`alias` 查询每条 v3 连接每分钟 240 次、`GET /v3/alias/…` 每个 IP 每小时 600 次；客户端退回 v2 目录时每条联系人最多试 8 个 Agent 名、每轮最多 60 秒。
- **旧进程**：迁移后还没重启的旧版进程写进来的联系人（`split` 为空）一律当作还没核对。
- **怎么看迁完了没有**：`morse status` 有一行 `contacts: one per address (identity v3) — …`（还有几条没向中转核对、备份在哪）；中转侧看 v2 登录数。

### 12.3.2 P3 的一部分：地址单独可用（ADR-081，2026-11-15）

- **能力位 `addr1`**：每个地址登录时发布，中转在 `address` 查询里带回；有它的地址能收不带设备证书的 v3 信封。没有它（对方还在 20261114170051 或更早）就不能按裸地址首次联系，报一行清楚的错。
- **原生路径**：按地址发的信由发信地址签名、不带证书、不带 handle，正文带 `addr: 1`；回执等同样由收信地址签。陌生地址的第一条信进好友请求（一个地址一条，ADR-037 的规则不变）；请求和拉黑按地址记（复用原来放 handle 的键位，不改表）；只有地址的联系人是 `a:<地址>`。
- **每个本机地址都能发**：`morse send --from <名字>` 和回信都由对应的地址签名；从第二个地址发的信不泄露第一个地址、handle 和设备。
- **自己的另一台电脑**：就是联系人，权限用 `morse contact set` 按联系人给（主人 2026-11-15 定：现在不做专门的权限机制；「`--group self` 即自己人」考虑过、已取消）。迁移进 `self` 的电脑照旧是 owner 档。
- **发信地址记的是地址本身**，不是名字：钥匙不在就不发，第一个地址绝不替别的地址出面；改名不受影响。应答只认「对方那个地址签的、送到我发信那个地址的」。
- ~~每个联系人记住他认识的是你的哪个地址~~（ADR-083 起：联系人直接属于你的某个地址，见第 12.3.3 节）（原文：他第一次写来时写到的，或你第一次写给他时用的），不带 `--from` 发信默认用它；`--from` 只管一条并提醒。旧 daemon 还没重启时，必须从指定地址发的信一律不提交、提示重启。升级前排着的信照旧从第一个地址发。
- **已知限制**：~~同时知道你两个地址的人看得出它们在同一台电脑上~~（ADR-083 已解决，见第 12.3.3 节）；拉黑一个地址挡不住对方换新地址，`morse.strangers: "block"` 才是真挡；请求区满了不挤掉旧请求，新来的被拒收并告知。旧 handle 永远不能长得像地址。
- 有旧 handle 的联系人照旧走 P2 的路径；局域网、直连暂不走原生路径。删 v2 前还差什么见 ADR-081 末尾。

### 12.3.3 每个本机地址有自己的联系人（ADR-083，2026-11-15）

- **不变量**：对方在我的地址 B 上能观察到的任何东西，都不取决于因为我的地址 A 才存在的状态。联系人、好友请求、拉黑、墓碑、去重、暂存、限速计数、传输状态全部按「（我的地址，对方）」记。
- 同一个对方可以分别是我两个地址的联系人——两条互不相干的联系人。旧 handle 的联系人和自己的电脑只属于第一个地址；v2 路径只以第一个地址说话。
- 命令不变，「我的哪个地址」统一用 `--from <名字|地址>`；只有一个地址的人看不到任何变化。备注在整台电脑上唯一。
- 迁移是 `user_version` 4（备份、幂等、可重入，纪律同 ADR-077）。
- 升级前的拉黑在迁移时的每个地址上都保留；之后的拉黑按地址。对方的公钥 / 预密钥缓存、预密钥的轮换时刻也都按地址分开。迁移后旧 daemon 没重启时，改联系人和发信的命令一律拒绝并提示重启。备份的手动恢复步骤见 [docs/guides/restore-contacts-backup.zh-CN.md](../guides/restore-contacts-backup.zh-CN.md)。
- 剩下的限制：中转（不是对方）能把同一条连接上的几个地址关联起来（也共用每 IP 的发送额度）；每个地址在不在线谁都能查；一封带设备证书的旧式信封能探出「这不是某台电脑的第一个地址」（只能看出这一点，删 v2 时消失）。

### 12.4 迁移期的新旧客户端

| 发件 → 收件 | 怎么通 |
|---|---|
| 新 → 新 | v3 信封，按地址 |
| 新 → 旧（对方还没更新） | 对方没发布 v3 公钥 → 用 v2：按设备 ID 封信，明文里带 `fromHandle` |

**自动更新**（ADR-039）每 6 小时检查一次，所以几台真机通常一天内都会更新。中转在 `/healthz`（和 v2 登录的 `welcome`）里宣布 `protocols: [2, 3]`，客户端看到之后才启用 v3。**关停旧协议的条件**：中转连续 14 天没看到 v2 登录，并且主人确认；然后发一版去掉兼容层的客户端，再部署中转。（主人 2026-11-16 改定：现在就删，分三期，见 ADR-091。）

## 13. 命令（主人 2026-11-14 定；命令面已由 ADR-074、ADR-079 实现，`address` 的二维码和 backup / restore 仍在 P3）

### 13.1 最终的用户命令

`morse --help` 只列 5 个（2026-11-14 主人定，ADR-079：一个 Agent 一个地址，`agent` 并进 `address`），git 风格：**名词用单数；不带参数 = 列出；带动词 = 修改**。

```
morse address                 我的地址（有几个时每个后面是它的备注名，只有一个时不显示名字；有旧名字时一行 old name；中转）
                              address add [备注名] / set [备注名|地址] --name <备注名> / remove <备注名|地址>
                              （ADR-088：和联系人一样用 set --name 起备注名，只是本地标签；rename 是隐藏的旧写法）
                              以后（P3）：二维码（名片）、address backup / restore
morse contact                 联系人（列出，末尾是好友请求）；contact <谁> = 一个联系人和实际生效的权限
                              contact add / set / remove / accept / reject / block / unblock
                              contact set 也设 attendant 权限（--cwd/--tools/--allow/--rate/--reset，ADR-070）
morse message                 待处理的消息（列出）；message <谁> = 和他的全部往来；message --id <ID> = 读一条
                              message --pull = 把发给这个会话的新消息拉进来；message --wait = 等到有一条来再返回
morse send <谁> <消息>        发信（--file 附件）
morse reply <消息ID> <消息>   回信
```

**两个名词**（ADR-088，2026-11-15 主人定）：**地址**是我的，**联系人**是别人——别人的 Agent 和我自己在别处的 Agent 一样是联系人。「Agent」只用来说谁在用 Morse，不是产品里要起名、识别、管理的东西。所以：

- 地址的备注名和联系人的备注名同一套做法（`address set --name` ↔ `contact set --name`），存在 `~/.morse/addresses/labels.json`，改它不动 `agents.json`（中转目录里的名字）；一个名字只能在一边。
- 只有一个地址时哪里都不显示名字。
- 一个会话用哪个地址，用地址的备注名说：`--from <备注名>`，或环境变量 `MORSE_ADDRESS=<备注名或地址>`；不设 = 发信用第一个地址、列表列全部。不按产品（Claude Code、Codex……）认调用者。
- 会话目标 `@<agent>:<会话>`、消息行里的收发 agent 一栏、隐藏的 `agent` 命令是 v2 的写法，和 v2 一起删。

`<谁>` 可以写你给他的备注、他的地址或链接；`--name` 设的就是你这边的备注（第 11 节）。读一条用 `--id` 而不是 `message <ID>`：`<谁>` 和 ID 前缀都是一串字母数字，放在同一个位置会猜错（ADR-074）。`morse agent …` 保留成隐藏别名（行为不变）；`agent default` 是空操作；不带名字的 `agent add`（配对码）和 `join <地址> --code` 是隐藏的兼容路径、P4 删除（ADR-077 第 17 条）。把自己的另一台电脑连进来：在那台装 Morse，两边互加联系人，按分组给权限。

**隐藏但照常可用**（`morse help --all` 列出，连同上面 5 个共 15 个）：`start`、`stop`、`status`（`--check` = 以前的 `doctor`）、`update`、`setup`、`hook`、`list`（`--conversations` = 以前的 `conversations`）、`done`、`connect`（也登记外部 agent 会话 = 以前的 `register` / `unregister`）、`plugin`（`plugin dispatch|attendant|ilink …` 和插件契约 `plugin claim|ack|nack|watch`）。其余旧命令（`inbox`、`history`、`read`、`contacts`、`requests`、`block`、`unblock`、`pull`、`monitor`、`doctor`、`register`、`dispatch`、`attendant`、`ilink`、`claim`、`watch`、`conversations`、`relay`、`pair`、`peers`、`device`、`join`、`invite` 等）保留成隐藏别名，行为不变；`pair`、`peers`、`join`、`invite` 在 P4 删除。`collab`、`flush` 已删除（ADR-074）。插件契约（ADR-051/052）的 JSON 形状只加字段，不改。

安装：`curl -fsSL https://morse.im/install.sh | bash` 新建地址；`… | bash -s -- --restore` 用恢复词找回。安装时检测本机装了 `claude` 还是 `codex`：只有一个就用它，两个都有就问一次。`--run` 写进本机配置，dispatch 和 attendant 按它选适配器，**不上线、不进签名**。

## 14. 安全分析

| 威胁 | 后果 | 对策 | 剩下的风险 |
|---|---|---|---|
| 中转运营者作恶 | 丢信、拖延、看元数据 | 地址自证、信封端到端（离线信箱里存的也是密封信封）；没有官方名字可伪造 | 元数据可见（含离线信箱的存取时间）；能做拒绝服务、提前删掉离线信；经冻结的旧别名第一次联系时要信中转（只限迁移前那几条，已有联系人靠同一把钥匙对上，不受影响） |
| 冒名（陌生人自称是 alice） | 你把他当熟人 | 没有官方名字可冒用，名字只是你自己的备注；新地址永远先进好友请求；从可信渠道拿链接，必要时核对地址后 8 位（第 17.4 节） | 只看对方自我介绍就同意 |

## 17. 加密是否达到最佳实践

**结论**：用的原语是标准的，签名和防中转换钥匙也做对了，但**没有前向保密**，组合方式是自己拼的，而且没有让人核对身份的地方。这三点达不到 Signal / Matrix 那一档。v3 第一期就补前两点的大部分，第三点因为地址可以自证，代价很小。

### 17.1 现在的代码实际怎么做

- **消息加密**（`src/cluster/e2e.ts`）：每条消息生成一把临时 X25519 钥匙，和**收件设备的长期 X25519 公钥**做 ECDH，经 HKDF-SHA256（salt = 临时公钥 ‖ 收件公钥，info 固定为 `morse-v1 aes-256-gcm`）得到一次性 AES-256-GCM 密钥，nonce 随机 12 字节。明文头（版本、from、to、临时公钥、nonce）作为 GCM 附加数据。整个信封（头、发件证书、密文）再用发件设备的 Ed25519 钥匙签名，是先加密后签名。每条消息的密钥都是新的，所以 nonce 不会重复。
- **公钥防替换**：加密公钥包由设备的 Ed25519 钥匙签名（`makeKeyBundle` / `verifyKeyBundle`），收件方按设备 ID（证书指纹）核对，中转换不了公钥；第一次核对后钉在 `peer-keys.json`（`src/cluster/morse.ts` 的 `recipientKey`、`pinKeyBundle`）。
- **签名**：每条经中转的消息都有发件设备签名（`open` 验签后才解密）；中转登录是挑战加签名（`relay-cf/src/crypto.ts` 的 `verifyLogin`）。
- **局域网**：消息以明文放在双向 TLS 1.3 里传（`src/cluster/secure-transport.ts` 的 `minVersion: 'TLSv1.3'`，ADR-034），证书指纹钉在信任名单上。
- **重放**：靠 `inbound_seen` 表按（发件设备、消息 ID）去重（`src/mailbox/db.ts`，`src/mailbox/mailbox.ts` 约 592 行）。
- **中转到客户端这一段**：wss，TLS 在 Cloudflare 终止；里面是上面那个端到端信封。

### 17.2 达不到的地方（照实写）

1. **没有前向保密**。收件方的 X25519 钥匙是长期的：`loadOrCreateEncKey` 生成 `identity/enc-key.pem` 以后从不轮换。临时钥匙只在发件这一侧。所以谁把中转或网络上的密文录下来，日后只要拿到收件电脑上的 `enc-key.pem`，就能把以前的消息全部解开。MORSE-MVP §5 已经写了「无前向保密的长期加密密钥」。
2. **钉住的公钥没有更新路径**：`recipientKey` 优先用钉住的公钥包，所以就算想轮换加密钥匙，现在的发件方也不会跟着换。
3. **组合是自己拼的**：ECDH + HKDF + GCM + 外层签名这一套，每一块都是标准原语，但拼法没有外部审查，也不是任何标准格式。它很接近 HPKE 的 Base 模式（[RFC 9180](https://www.rfc-editor.org/rfc/rfc9180)），但标签和 KDF 输入都不一样。
4. **发件人身份在明文里**：信封头的 `from` 和发件证书 `cert` 不加密。中转本来就知道是哪台设备发的，但信封一旦被转存或转交，任何经手的人都看得到发件人。签名在密文外面，所以也没法隐藏。
5. **信封里没有时间**：没有「太旧就拒收」这一条；`inbound_seen` 从不清理，会一直变大。
6. **局域网上的消息本身没有签名**：链路有 TLS 1.3 的前向保密，但存进信箱的消息没有发件人签名可以事后核对。
7. **本机明文存储**：`mailbox.db`、`inbox-files/`、分块暂存（ADR-038）都是明文；私钥文件 0600、不加密（ADR-028「不防的」）。前向保密保护的是被截下的流量，不保护电脑上已经存下的东西。
8. **没有身份核对**：按 handle 第一次联系时，信的是中转目录说「这几台设备属于他」（ADR-031/034）。没有安全码，也没有指纹比对界面。

### 17.3 v3 怎么改

**原则：不自己发明。** 用 IETF 标准的 HPKE 做单条消息加密：Base 模式，DHKEM(X25519, HKDF-SHA256)、HKDF-SHA256、AES-256-GCM。实现用现成库 [hpke-js](https://github.com/dajiaji/hpke-js)（本机 Node 22 没有内置 HPKE，已核对）。等 Node 内置之后再换过去。备选是 libsodium 的 [sealed box](https://doc.libsodium.org/public-key_cryptography/sealed_boxes) 加 `crypto_sign`，构造等价，但要多一个原生依赖。签名仍用 Node 自带的 Ed25519。

**单条消息的格式（P1 就做）**：

- **先签名、再整体加密**：发件地址的公钥、`to` 地址、发送时间 `ts`、消息正文放在一起，用发件地址的 Ed25519 钥匙签名，再把明文和签名一起用 HPKE 封给收件方。签名里写进收件地址，防止收件人把一封签好的信原样转给第三方冒充（「暗中转发」问题）。外层只剩路由要用的 `to`，发件人身份不再以明文出现在信封里。
- 收件方拒收 `ts` 早于 31 天（发件箱最长等 30 天）或晚于当前时间超过 10 分钟的信封；`inbound_seen` 只保留 31 天。
- 局域网也传这同一个信封（第 8.1 节），每条消息都可以核对发件人签名。

**前向保密（分两步）**：

1. **P1：签名预密钥，按周轮换**（就是 Signal [X3DH](https://signal.org/docs/specifications/x3dh/) 里的 signed prekey，不用一次性预密钥）。每个地址发布一把用地址钥匙签名、带有效期的 X25519 预密钥，每 7 天换一把；旧私钥保留 8 天，给在途和离线信箱里的信用（信箱最多存 7 天，多留 1 天余量），然后删除。HPKE 封给当前的预密钥。**和离线投递的配合**：对方不在线时，信封存进中转的离线信箱（最多 7 天，第 8.3 节），封好以后不再变，所以旧私钥要保留到信箱期满；发件方自己连不上中转时，信留在本机发件箱，**每次重试都重新封**（今天 `morse.ts` 约 1722 行的发送尝试就是每次重新 `sealFor`），重试前先刷新对方的预密钥；收件方遇到不认识的预密钥，就回一条「请用新预密钥」，发件方刷新后重发。效果是：电脑在 T 时刻被攻破，能解开的被截流量只有最近约两周的，而不是全部。
2. **以后：活跃的对话用双棘轮**（[Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)），做到每条消息都有前向保密，并且被攻破后能自愈。实现用 Matrix 的 [vodozemac](https://github.com/matrix-org/vodozemac)（Olm，Apache-2.0，Element 在用）。**不用 libsignal**：它是 AGPL-3.0（已核对仓库的 LICENSE），和客户端打算用的 Apache-2.0（ADR-058）冲突。双棘轮要求每个联系人的会话状态在多台电脑之间一致；混合模型下每个 Agent 只在一台电脑上，正好满足。代价是会话状态要随 Agent 搬家，状态丢了要重建会话。建议等 P4 之后单独立项。

**为什么不用 Noise**：[Noise](http://noiseprotocol.org/noise.html) 的 IK / XX 握手是给双方同时在线的连接用的。Morse 的信要能在对方离线时留在发件箱里，等对方上线再送，所以单条消息不适合用 Noise。双方都在线的链路（局域网通道、到中转的连接）已经由 TLS 1.3 提供前向保密，再套一层 Noise 不增加什么。

### 17.4 身份核对（安全码）

- **地址本身就是指纹**：地址是公钥的哈希（约 128 位）。从对方本人那里拿到的地址（当面、可信的聊天），不需要再核对。
- 需要核对的只有三种情况：**陌生人主动发来的第一条**（只知道对方的地址，不知道背后是谁）、**链接是从不可信渠道转来的**（比如群里转发的名片），以及**经冻结的旧别名找到的**（信的是中转，第 12.3 节）。`morse contact add` / `accept` 会打印完整地址，并提示「想确认，就请对方念一下他 `morse address` 的后 8 位」。确认后联系人标记「已核对」。没有官方名字，也就不存在「名字被改指到别人」的问题。
- **信任从地址开始**：每个地址自证，一个地址核对一次。没有 CA，也没有设备证书链；你自己的几个 Agent 之间也是一个个地址各自核对（互加联系人时）。
- 以后可以加 Signal 式的「双方安全码」（两个地址公钥合成一串数字，当面比对），但地址已经是完整指纹，价值有限，不急。

### 17.5 中转（和网络）仍然看得到的元数据

- 每个信封的收件地址；发件方登录的是哪个（或哪几个）地址、什么时间、多大。分块传文件时，看得到块数和每块大小。
- 哪些地址从同一条连接或同一个 IP 登录，进而推断出「这几个地址在同一台电脑上」；IP 地址和大致位置。
- 在线与否、上线下线的时间。
- 查询记录：谁查了哪个地址、哪个旧别名、哪个预密钥。
- 公开清单、成员吊销列表、旧别名表（这些本来就是公开的）。
- 离线信箱：每条信存了多久、什么时候被取走、哪些到期没送达。
- WebRTC 信令：哪两个地址在直连传文件、什么时候；直连时双方能看到对方的 IP。
- 好友请求的模式（新地址在短时间内给某个地址发小信封）。
- 日志：现在 `relay-cf/src/hub.ts` 打印设备 ID 前 7 位、handle、字节数、在线/离线；v3 改成地址前 7 位，不再有 handle。

**能便宜做的**：信封长度补齐到固定档位（例如 1 / 4 / 16 / 64 KB），P1 一起做。**以后再说**：像 Signal 的 [sealed sender](https://signal.org/blog/sealed-sender/) 那样，连中转也不知道是谁发的。这要求登录和发送分开，并配一套匿名投递凭证，改动大，等有真实需求再做。
